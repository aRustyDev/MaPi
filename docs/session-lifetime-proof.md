# Session lifetime and operator routes

The pinned v0.7.0 server has a **server-wide** session lifetime configuration; it does not ship a project-level session policy API. Its default is 24 hours and its maximum is 720 hours. `POST /sessions` creates a separate anonymous building session with a 10-minute lifetime; a completed sign-in upgrades the session and resets its lifetime. Reads do not extend expiry.

MaPi now accepts optional `MAPI_SESSION_DEFAULT_TTL` and `MAPI_SESSION_MAX_TTL` Worker variables. They use Go duration strings such as `2h`, `30m`, or `4h30m`, matching the native configuration format; the HTTP exchange request continues to use ISO-8601 durations such as `PT2H`. Omitting either variable retains the corresponding native default. The original 24-hour/720-hour behavior is unchanged when neither variable is set. Both Worker entry points and the Go reactor reject explicit non-string values, including JSON `null`. The reactor uses the upstream `SessionConfig.Validate` checks: both durations must parse and be positive, and the default must not exceed the maximum. Values outside Go's representable duration range also fail to parse. Invalid explicit configuration fails reactor initialization without logging the configured values. On an existing application object, `ready` and `configurationReady` become false after initialization or restart with invalid settings. The operator status request always validates reactor initialization; the ordinary default hot path remains lazy and must not be interpreted as a separate full-service health check.

For a local application, add the variables to the ignored `.dev.vars.app`; for deployment configure them as Worker variables for the appropriate Wrangler environment. The reactor reads the settings at initialization; use a controlled deployment/restart strategy and verify all relevant objects have adopted the new version. A configured change applies to **new** exchanges, not the expiry already persisted on existing sessions. No staging configuration was changed or deployed for this proof.

After generating the normal fixture and installing the repository dependencies, run:

```sh
node scripts/build-session-extra-test.mjs
node scripts/test-session-extra-parity.mjs
node scripts/test-session-config.mjs
node scripts/test-session-overflow-probe.mjs
node scripts/build-console-flow-proof.mjs
MAPI_TEST_SESSION_CONFIG=1 node scripts/test-console-flow-proof.mjs
node scripts/test-console-flow-proof.mjs
node scripts/parity-inventory.mjs --check
```

These tests need the pinned Go toolchain, Playwright Chromium, local loopback and the Console assets. The first build uses a temporary pinned Git archive with the existing overlay. `mapi_session_extra` adds anonymous session creation and operator get/query only to its private test reactor; it does not change public route mounts. Native and workerd comparisons cover no-auth and session-only denial, creation with the wrong project, anonymous TTL, proof of the session token before step-up, token supersession on upgrade, cursor paging and malformed cursor, 24-hour default, explicit one-hour and 720-hour maximum, invalid/negative TTL, non-sliding reads, a short-lived expiration, operator revocation and immediate rejection of its old cookie. An invalid TTL leaves the one-time handoff usable and adds no `session.established` audit. Workerd fault injection confirms an exchange audit failure rolls back and leaves the handoff usable; native audit fault injection was not exercised. The operator test's independently valid foreign credential returns 404 `sess.not_found` on native and 401 `auth.unauthorized` in the object-fenced Worker. The fixture stores both projects in one test database, so it does not establish cross-object authorization parity.

The configured-default test runs native Nextgen with `NEXTGEN_SESSION_DEFAULT_TTL=2h` and `NEXTGEN_SESSION_MAX_TTL=4h` and the Worker with the corresponding MaPi settings. Both issue a 2-hour default and reject an override above 4 hours without consuming the handoff. Both also accept a 900-hour exchange when configured with a 1,000-hour maximum; the native configurable range is not artificially capped at its default. A worker restart with a new valid default leaves an existing session's exact expiration unchanged and applies the new default to a new session. Malformed, zero, negative, reversed, overflowing, and non-string binding values reject authentication in the test object. A direct Go/Wasm initialization probe also rejects explicit null, number, boolean, object and array duration values. A real app-object browser test confirms the configured default and that a persisted project's status is not ready after restart with a default greater than its maximum, a malformed master key, or a missing master key; repeated readiness checks, official application login, and Console runtime fail closed for the configured-TTL cases. Repeated operator status requests also report not ready for malformed or missing master keys with default TTL settings. A second browser run verifies the unchanged default path.

The SQLite session expiration uses signed 64-bit nanoseconds. In one local boundary test, native and workerd both rejected an exchange for `PT2562047H` with `sess.exchange_conflict`, left its handoff usable, and did not write a session-established event. A TTL calculated to end two hours before the signed-nanosecond boundary succeeded on both with the expected expiration and a readable session. This is a tested boundary case, not a promise that every near-boundary duration or long-running object configuration is safe.

These are local tests, not a hosted rollout, load test, or complete parity suite. They do not prove all TTL values, all delegated permissions, application-scoped policies, request auditing, release and rollback compatibility for environment changes, distributed rollout, or behavior of other independently configured service compositions. The private FAPI and bearer issuer test compositions use their own session-service instances for validation; no issuer configuration, public issuer route, expiry policy or refresh-token behavior is changed here. The anonymous/get/query routes remain unexposed until full ingress, cross-project authorization and hosted resource checks pass. The existing account-enumeration issue in the official Console flow remains open.
