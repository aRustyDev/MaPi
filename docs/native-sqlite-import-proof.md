# Local native SQLite import proof

`node scripts/test-native-import.mjs` freezes a synthetic Nextgen v0.7.0 native SQLite server, copies its entire database into an initially empty local SQLite Durable Object, and exercises the pinned Go handlers. This is an isolated compatibility test, not a production migration or project extraction tool. It requires Node 24 or later, installed dependencies, loopback access and the normal `npm run build` output including `worker/generated/nextgen.wasm`. Run it from the MaPi root. The test uses uniquely named ignored generated files and deletes them and its temporary directory on exit; do not run two instances concurrently.

The source contains two separately provisioned synthetic projects. Before stopping native, the test creates a password user in each, active sessions, a revoked primary session, an outstanding primary handoff, and a foreign session, attempt and handoff. It copies the native master key into a mode-0600 temporary local development environment and exports the complete database's schema and rows, preserving 64-bit integers, blobs, generated-column rules and indexes. The source is stopped before snapshot extraction; it is not tested under concurrent native writes. A `transactionSync` on the destination applies the snapshot and version marker together. The test checks a wrong project ID, a fault after partial schema/data application, and a repeated import are rejected, with no persisted schema after rollback. In local Miniflare, its own `__miniflare_do_name` table is excluded from the empty-object check.

The imported project ID and user ID match the source. The test hashes and compares **every field** of all primary-project audit records using exact SQLite integer and blob representations, without logging their contents. A source active session remains readable, a source revoked session remains rejected, a source handoff exchanges once, and the original password produces a new session through the upstream Go verifier. An additional revocation is immediately authoritative, and active and revoked sessions retain their states after object eviction. These checks are synthetic and local; the snapshot is intentionally bounded to 2 MB and 10,000 SQL statements.

**The tenant-boundary acceptance gate fails.** This exporter copies the *whole* native database: the test confirms that the second project's project, user, session and attempt rows physically exist in the first project's object. A real, native-issued credential and cookie for that foreign project are rejected by the tested authentication-attempt, challenge, handoff, exchange, session read, CSRF and revoke routes, including self-revocation with a real session-bound CSRF token. Mixed foreign/primary credentials and project IDs are also rejected for the tested attempt creation and session read. This request fence does not remove the data or prove all callers and other routes are isolated. Project filtering is not implemented because teams, grants, cross-project principals, shared catalog/reference records and other dependencies require a complete ownership and integrity analysis. Do not use this exporter to populate a per-project object.

The script inserts raw SQL generated from a locally created trusted synthetic SQLite file; it has no authentication, untrusted-input validation, snapshot signature, encryption-at-rest or safe transport. Its local diagnostic endpoints and injected failure/eviction methods must never be deployed. Native schema metadata beyond the copied tables and schema objects, application-version compatibility, large databases, streaming, resumability, canonical ordering, full referential reconciliation, foreign-key enforcement at all boundaries, live source write fencing, cutover and rollback are not established. Passkeys, identity providers, grants, issuer keys and their RP/issuer portability are not verified. The test imports the source master key only to exercise the credentials and cookies; real key custody, rotation and recovery require separate design.

This experiment deliberately preserves active sessions and a pending handoff to test compatibility, **not** to define a restore policy. Before reopening traffic after a data restore, the roadmap requires invalidating affected sessions and pending handoffs and advancing a non-reused recovery era. No actual PITR, recovery-era fencing, hosted Cloudflare execution or load measurement is covered here.
