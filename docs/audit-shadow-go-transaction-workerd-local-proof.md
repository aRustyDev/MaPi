# Go-to-host shadow start: local Workerd diagnostic

The unmounted `shadow-go-transaction-diagnostic.go` uses the actual current Go `cloudflarewasm.Transaction` and SQL driver. Inside the Go callback it reads a synthetic permission row, writes a business marker, invokes a diagnostic host import, and writes another marker. The host import refuses calls outside its active `transactionSync` callback and invokes `beginShadowInTransaction` without reentering Go. The host callback propagates Go errors by rolling back the enclosing SQLite transaction.

`node experiments/audit-snapshot/shadow-go-transaction-workerd-test.mjs` passed in disposable local Workerd with SQLite. A denied synthetic permission prevented the host call; an injected error after snapshot creation rolled back both business-marker writes and all shadow schema; a successful attempt committed both markers and an active shadow. The test also checked that its host callback rejects a call when no transaction is active. The runner builds a fresh Go 1.26.9 WASI module offline from the current overlay bridge files in a disposable minimal module and uses the existing generated baseline event DDL and indexes. Its single local session completed exit 0; no test process remains live.

This is an integration of the Go transaction mechanism and snapshot-start seam, not the pinned API handler or production owner. The permission row and host authorization callback are test doubles: no real bearer, project-access or platform-operator decision was exercised. The diagnostic import is not mounted in the application. It does not establish handler validation/error precedence, revocation semantics, owner authority, complete bounded snapshot, recovery, hosted behavior, or that the Go/JS host contract is safe for other reentrant calls. The pending handler and transfer tests, stopped importer/manifest/registry actions, Woven deployments and AWS resources were not touched.
