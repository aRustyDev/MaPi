# Experimental project relocation proof

This document retains the chronology of local prototypes and their limitations. Statements about the initial standalone prototype, bulk fixture, or proposed hosted procedure describe that evidence at the time; later local integration and isolated hosted results are recorded below and in `phase1-hosted-handoff-repeat.md`, `phase1-hosted-restart-rehearsal.md`, `relocation-prefreeze-local-proof.md`, and `pending-owner-prototype.md`. Those later results do not establish sign-off for the current source or authorize a real move.

`worker/relocation.js` is a standalone local proof, **not wired into the app, registry, or staging deployment**. Run `node scripts/test-relocation.mjs` to exercise it with local workerd. The test uses synthetic schemas, not the complete Nextgen database; it is not evidence that a real project can be relocated.

The protocol keeps a source fence and registry generation durably in their respective SQLite objects. A coordinator reserves a move, freezes writes on the source, takes a deterministic bounded snapshot, stages it transactionally in an empty destination, compares the source and destination digests, then changes the registry route and generation in one registry transaction. The destination is activated after cutover and the source retired. Each checkpoint supports an identical retry after interruption or eviction. There is no atomic cross-object commit: after the source freezes, availability may be interrupted until retries finish. There is no rollback or thaw path in this proof. Never make either owner writable on an uncertain route.

The proof rejects snapshots larger than 512 KiB or 10,000 rows and reads one row at a time. This is a deliberately small bounded transport, not a production import mechanism. The caller must supply the complete, ordered list of tables; schemas and migration version must match, all expected data and reference records must be included, and snapshot ordering must be stable across retries. Large databases need a resumable, integrity-checked, bounded chunk transport and a tested reconciliation procedure. The current offset reads are not intended for large datasets. Only SQLite tables explicitly supplied are copied; metadata, SQLite sequences, non-table state and external state are not automatically transferred.

The control API in this proof trusts its caller. Registry route and owner states passed to commit, activate and retire must be read from the authoritative objects by an authenticated coordinator, never accepted from an HTTP client. Production integration must prevent forged or stale control proofs, concurrent coordinators, object-name reuse, replayed checkpoints and overlapping moves, and must establish that the registry's current generation still matches when coordinating activation. A move must not be considered complete until activation and retirement are both confirmed. There is no general-purpose cross-object transactional guarantee.

Most critically, every mutation must verify the local project state and route generation **inside the same synchronous transaction as the mutation**, and ingress must propagate the generation from the authoritative registry. This includes authentication-attempt and challenge changes, handoff and session creation and exchange, session reads that update state, revocations, audit writes, admin/configuration changes, background work and recovery. Guarding only management writes permits authentication or session mutations to race the snapshot. Reads and cached routes also need an explicit policy during cutover. The existing app and registry do not implement these guards; this prototype must not be used for live relocation without that integration and failure testing.

The local test checks stale write rejection, conflicting moves, idempotent retries, failed import rollback, typed 64-bit integers and blobs, oversized snapshot rejection, registry cutover, and survival of object eviction. It does not establish migration of an upstream schema, correctness of all mutation paths, snapshot security, production scale or Cloudflare hosted performance.

## Resumable chunked transfer: local proof

`worker/relocation-chunks.js` is a separate experiment using the same source fence, destination stage and registry generation proof. It is **not integrated with the live app, project registry, recovery procedure, or production routing**. The source prepares each chunk durably before hashing it, checkpoints its position and hash chain after hashing, and returns the same content on retry. The destination checks the digest, sequence, table, column list and offset; it inserts each chunk and advances its checkpoint in one SQLite transaction. Replayed chunks must match the recorded digest. The destination stays non-writable in `importing` state until the last chunk is committed and checked, then becomes `staged`; registry cutover still compares the frozen source's final digest with the staged destination's digest. These separate objects do not share an atomic transaction.

The transfer is limited to **128 KiB encoded per chunk and 64 rows per chunk**. A row that does not fit is encoded per source read and split into 80 KiB byte fragments. Text and blobs use base64 in the fragmented row envelope to bound encoding expansion. The destination checkpoints fragments independently and inserts the reassembled row in the same transaction as the final fragment checkpoint. The sum of row value bytes is capped conservatively at 8,000,000 minus 4,096 bytes for SQLite record overhead, and the encoded envelope is capped at 12 MiB. Both limits are checked during export and reassembly. The actual SQLite row limit still applies, and hosted memory use for near-limit rows is unmeasured. The complete table list and dependency order are supplied by trusted coordination code. Foreign keys are checked **before every chunk commits**: parent rows must already exist or be included in that same transaction. Cycles spanning chunks, deferred cross-chunk constraints, and complex upstream schemas require a different import design. The local test intentionally supplies an invalid FK order and verifies both rows and checkpoint roll back. Checking only at deferred commit caused workerd to reset the object, so this proof checks inside the transaction.

`node scripts/test-relocation-chunks.mjs` runs the isolated workerd test. It transfers 1,284,233 encoded bytes in 14 chunks, interrupts an export after content is saved but before its hash is finalized, injects an import failure after a row write, retries chunks, evicts both objects mid-transfer, rejects tampering, out-of-order and conflicting replays, checks FK constraints, preserves signed 64-bit extrema and blobs, performs registry cutover, and rejects stale writes. Synthetic data and schemas are used; there is no real Nextgen project import, hosted test, large-tenant load test or production recovery rehearsal.

The chunk test also transfers fragmented binary and multibyte text rows, tests
out-of-order and conflicting fragments, interrupts before hashing, evicts both
objects, and retries a rolled-back final insert. It rejects a 7,996,000-byte
value and a fragment advertising more than the reassembly limit. For a normal
composite primary key, `EXPLAIN QUERY PLAN` now confirms an indexed seek,
including a signed 64-bit key. A table with an explicit collation keeps binary
comparison semantics and is checked across multiple pages.

## Pinned-schema local fixture

`node scripts/test-relocation-nextgen.mjs` uses a fresh local workerd store,
the generated Nextgen baseline, and synthetic rows in ten project tables.
`MAPI_LARGE_IMPORT=1 node scripts/test-relocation-nextgen.mjs` seeds 10,000
users, attributes and synthetic password rows, plus 100,000 synthetic events.
It checks bounded chunks, injected export and import failures, replay, object
eviction, checkpoint continuity, matching per-table row counts and canonical
SHA-256 digests, matching final hash chains, and zero foreign-key violations.

One large local run before the indexed-seek change seeded in 5.66 seconds and
transferred 166,977,197 encoded bytes in 2,040 chunks over 651.36 seconds.
All ten table counts and digests matched. The pre-optimization query plan
scanned the events primary-key index. After the change, the same large fixture
seeded in 5.98 seconds and transferred the same bytes and chunk count in
52.87 seconds. All ten counts and digests again matched, and an
`EXPLAIN QUERY PLAN` check confirmed that the events keyset seeks on its
primary-key index. These measurements are from local workerd.

This fixture contains synthetic password and encryption-key values and direct
SQL inserts. It does not establish credential portability, real Go login,
complete Nextgen table or reference closure, cross-project isolation, hosted
resource usage, or safe migration of an existing project.

## Go-provisioned fixture

After `npm run build` and `npm run baseline`, run
`node scripts/test-relocation-go-fixture.mjs`. The test generates a fresh
master key and synthetic passwords in a private temporary directory, starts
local workerd, and deletes the directory afterward. It provisions two projects
and users through the real Go-backed application, creates active and revoked
sessions, and copies one project's 26 fixture tables through the standalone
chunk protocol. It checks the source and destination table counts and digests,
checks the pre-existing authorization catalog and migration-ledger rows match,
and copies the origin through a test-only control method.

The local run preserved the project ID, one user, and 27 historical audit
events. The copied active session and a fresh sign-in with the original
password passed, the copied revoked session remained rejected, and a foreign
cookie was rejected. The other project's session remained valid while each
source chunk was requested.

This is a small synthetic fixture. Its table manifest covers the populated
tables of this particular setup, and it checks for unaccounted populated
tables before the move. It does not establish a complete ownership manifest
for other projects or cross-project grants. The standalone relocation fence
is not connected to application mutation admission. The origin is copied
manually and activation uses a test-constructed route proof. The test does
not switch a registry route or exercise hosted cutover, interrupted recovery
or concurrent writes to the moved project. Workerd restart responses are
retried only for repeatable control and read calls. User creation, login and
session calls fail visibly if interrupted.

This is not yet a safe migration tool. Chunk content is copied into source SQLite storage and has no garbage collection or retention policy, so it can expose sensitive data and consume substantial quota. Exports use durable primary-key cursors and require a non-null, explicit primary key for each table. Per-row reads remain deliberately simple. An unfinished legacy offset checkpoint cannot resume and must be restarted from a fresh, fenced move. Imports need an explicit complete table and schema-version manifest, canonical ordering, coverage for triggers, indexes, generated columns, SQLite sequences, migration-owned reference rows and other state, a reconciliation mechanism, encryption and access controls, disk quotas, rate limits, and safe cleanup. This stream hashes chunks for integrity; it does not authenticate the coordinator or authorize a move. A corrupt or untrusted caller must never be allowed to supply source status, destination status, route proof, table list, or chunks without a trusted control channel and source verification.

Most critically, integrate durable project ownership and generation fencing across **all** existing app mutation paths, including password attempts, flow submissions, handoffs, session exchange and revocation, audit writes, configuration, maintenance and recovery. The check must share the mutation's authoritative transaction. Source and destination reads, background jobs, in-flight requests, cached routes, retries and cross-project grants also need a cutover policy. Freeze must happen before the snapshot, destination must stay unavailable until registry commit, and stale owners must reject requests after switching. A crash can leave the source frozen or destination partly staged; an authenticated coordinator must resume idempotently without making two owners writable. This proof has no rollback/thaw or automatic conflict resolution.

A point-in-time restore can roll back fence, import, registry or project records independently. Before reopening traffic after restore, establish which copy owns the project, fence all others, reconcile the registry and generations, invalidate affected sessions and pending handoffs, and verify audit and credentials. Restore, copy, export retention and movement of signing keys require an explicit security and operational design. The current app's restore code and registry do not enforce any of this; running this test is not authorization or evidence to move real user data.

## Pinned manifest and reserved destination preparation

`node scripts/test-relocation-manifest.mjs` exercises the local workerd manifest and chunk helpers after `npm run baseline`. The source must have a frozen, matching owner fence. The manifest checks the pinned baseline schema and project identity, classifies all 26 optional issuer and DPoP tables and their 13 indexes from the checked-in overlay, validates same-project rows and reviewed principal references, and rejects unknown schema and unresolved FAPI prompts. `node scripts/generate-relocation-issuer-schema.mjs --check` checks the generated issuer schema against that overlay.

The optional `mapi_revision_clock` and `mapi_revision_scopes` tables must be present together or absent together. The manifest requires one aggregate row, nonempty v1 scope keys and integer stamps, with the aggregate at least the maximum scoped stamp. The destination copies and reconciles both tables without losing integer precision. The local 85-table fixture includes values above 2^53, `args: null` and arrays containing null, malformed pairs, and a destination eviction and retry. Registry-anchored recovery of the revision high-water mark is a separate requirement.

The fixture transfers and compares 83 pinned and runtime tables using bounded digest pages, including a SQLite sequence above JavaScript's exact integer range. The reserved destination helper verifies the exact generated baseline reference rows before clearing them, creates only the reviewed issuer schema, and records a durable preparation marker. Retrying preparation after import begins cannot erase imported rows; altered reference data and conflicting retries are rejected. The origin, schema version, recovery epoch and sequence are separately restored and reconciled. `worker/generated/baseline.json` is build output, so it must be regenerated with `npm run baseline` to include reference rows.

These tests are local synthetic evidence, not a hosted relocation rehearsal. Cross-project principal references and unreviewed tables fail closed; migrating such data needs a separately reviewed ownership policy. Digest equality is a prerequisite to cutover, not an authentication or authorization mechanism.

`MAPI_LARGE_IMPORT=1 node scripts/test-relocation-nextgen.mjs` now uses the frozen-owner manifest, reserved-destination preparation and metadata reconciliation. A local run seeded 10,000 users and 100,000 events, with attributes, synthetic password hashes, teams, same-project membership and grant, a release and deployment, an encryption-key record, a session and handoff, nanosecond timestamps, and synthetic rows in the reviewed issuer tables. The manifest covered all 83 tables, though many had no rows. It transferred 167,332,480 encoded bytes in 2,117 chunks, with a largest chunk of 109,701 bytes and three fragments for a 180,000-character attribute. Transfer took 44.13 seconds (3.79 MB/s and approximately 2,946 bulk fixture rows/s). Counts and canonical digests matched on 2,115 bounded reconciliation pages, and both foreign-key checks were empty. The test injected an interruption before export digest finalization and after an import row write, replayed a committed chunk, and evicted and restarted both objects at a durable checkpoint.

This bulk run uses synthetic credentials and table inserts; it does not prove those credentials, sessions or issuer rows work through Go handlers. The separate small Go-provisioned fixture verifies existing login and session behavior but does not exercise the full 128 MiB dataset. The run does not measure storage overhead or total isolate memory and does not verify a concurrent second project. No hosted staging rehearsal, live issuer verification, encrypted export retention, or independent-registry PITR reconciliation is established by this evidence.

### Hosted rehearsal investigation

The production `RelocationCoordinator.advance` is a private Durable Object RPC; each call advances a bounded chunk or digest page. Cloudflare's [local development documentation](https://developers.cloudflare.com/workers/local-development/#remote-bindings) says Durable Object bindings cannot themselves be remote bindings and describes a remote service binding as the proxy pattern. `worker/relocation-rehearsal-control.js` is an unconfigured candidate proxy: it requires an operator secret, calls only the coordinator, and takes the origin, project ID and move ID solely from its environment, not the request. `scripts/advance-rehearsal.mjs` drives a loopback-only caller until completion or a bounded call limit, and stops on a failed call for inspection. `node scripts/test-relocation-rehearsal-control.mjs` and `node scripts/test-advance-rehearsal.mjs` check authorization, target selection and loopback constraints. This is not a deployment configuration or proof that its target is synthetic.

Before using it, export and bind the coordinator class in a fresh, separately named owner Worker and namespace; prove the Worker version and namespace IDs belong only to the newly provisioned synthetic fixture. Deploy the proxy with **no route, no workers.dev, and no preview URL**, bind it only to that owner, and use a private remote service binding from a loopback-only operator client. Verify the route's project ID, origin and owner, configuration and secrets independently; compare before/after records and exercise interruptions and the second project. `MAPI_FENCE_WRITERS_DRAINED=1` is an operator assertion, not evidence that old writer versions have drained. None of these hosted steps has been run or validated here, and the proxy must not be bound to the existing Woven owner.

The local integration command is `node scripts/test-relocation-rehearsal.mjs` after `npm run baseline`, `npm run build:login-assets`, and `npm run build:phase1-owner`. It creates isolated temporary names, local bindings, keys and data, then removes them. A local run completed 115 coordinator advances, restarting the caller during import, reconciliation and after registry commit. It preserved the initial project ID, a working pre-move session, one user and 17 audit rows; five other-project sign-ins succeeded during the move, and the moved user's credential was rejected on the other project. The coordinator compares the frozen source and staged destination by table and digest before committing. This test restarts the caller, not the owner or coordinator; the separate local real-owner test injects those interruptions.

For review of a future hosted rehearsal, `node scripts/relocation-rehearsal-config.mjs <new-directory>` generates fresh random names and owner, router, private control and local caller configurations using `CLOUDFLARE_ACCOUNT_ID` and `MAPI_REHEARSAL_WORKERS_SUBDOMAIN`. It does not deploy. The owner and control start disabled for moves; all generated Workers request 100% invocation logging. Run `node scripts/relocation-rehearsal-provenance.mjs <directory> before` with a read-only `CLOUDFLARE_API_TOKEN` to save the script and namespace inventory before creating anything. Following a separately reviewed creation of the three synthetic Workers, record the reviewed version UUIDs as `approved-versions.json` with `owner`, `router`, and `control` keys, then run the same command with `after`. It checks unique new SQLite namespace IDs, expected owner classes, absent local caller deployment, no control routes or public subdomain, unchanged config hashes, active 100% versions, version bindings and deployed log settings. It deliberately fails closed on incomplete API inventory. A fresh-name before check against the existing Woven account passed read-only: 22 scripts and 19 namespaces on one page. The live namespace response omitted `total_pages`; the checker now derives it from the reported total count and page size. The after-deployment API shapes, deployed version bindings and log settings have only mocked coverage and remain unverified.
