# Synthetic archive staging policy

Status: **policy only; not provisioned or verified**. This is a seven-day minimum for a disposable Phase 1 rehearsal, not Woven's production retention policy, a verified recovery archive, or authorization to move the real singleton. Use only synthetic project data, synthetic credentials, and a new synthetic archive key. The existing source chunks, owner objects, registry, Workers, bindings, and deployments are not cleanup targets.

## Isolation and roles

Create a fresh run identifier `mapi-p1-syn-<UTC date and time>-<128-bit random hex>` and record it in a run inventory. Use it in new resource names and object prefixes; verify by read-only inventory that every exact name is unused before creation. Verify the intended staging account and explicitly identified recovery account against an operator-provided allowlist. A name collision, unknown account, pre-existing binding, or uncertain ownership stops the run; never repurpose an existing Woven resource. A disposable local R2 binding is useful for development but does not meet hosted evidence below.

The rehearsal requires these distinct authorities and failure domains:

| Role | Synthetic authority | Required access and separation |
| --- | --- | --- |
| Move writer | New staging Worker and source owner | Read the frozen synthetic source, write archive ciphertext under this run's prefix, and use only the current synthetic archive key through an authorized interface. No archive delete, overwrite, retention administration, or escrow administration. |
| Archive administrator | A separate archive storage account and administrator | Configure retention and writer/recovery grants for the new synthetic bucket; no access to plaintext archive keys or the source project. |
| Key custodian | An independently administered KMS or protected escrow in a separate administrative failure domain | Recover the immutable synthetic key version and authorize the recovery operator; no administrative access to archive storage or the source project. The mechanism and its actual independence still need to be selected and verified. |
| Recovery operator | A separately authenticated recovery environment and narrowly scoped credentials | Read the archive and use the approved key-recovery operation; no write or delete access to the source or archive. Recreate this environment without the move writer's credentials. |

Different prefixes, bindings, API tokens, or resources controlled by the same administrator or account do not establish independent custody. Record the actual provider, account, administrators, recovery method, access grants and common failure domains before the rehearsal. If independent authority cannot be provisioned or demonstrated, the archive gate remains open. The document does not select a provider or assert that the existing account has the required permissions.

## Keys, retention and disposition

- Generate a fresh high-entropy synthetic data-encryption key per archive using the eventual reviewed writer. Record only its immutable identifier and version in the run inventory and authenticated archive metadata. The writer and recovery path must use an independently controlled wrapping or escrow mechanism; never put plaintext keys in repository files, source SQLite, archive objects, logs, or test output. Local tests use synthetic keys and must not be treated as a production key-recovery proof.
- Before the first archive write, configure an **indefinite** lock on the new run's archive prefix and restrict authority to change that lock to the archive administrator. Keep it in place for the rehearsal. Cloudflare documents R2 [bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/) for preventing deletion and overwrite, and administrators can change lock rules; therefore a rule alone is not proof of independent administration or permanent retention. Confirm the effective rule and independently test the writer's denied overwrite and deletion without modifying any existing resource.
- Retain every ciphertext object, final seal, trusted source commitment, its verification material, and the recoverable key version for **at least seven complete 24-hour days after independent verification of the final seal**. This is the synthetic minimum, measured from that verification's recorded UTC timestamp; objects written before the seal must remain protected through the same deadline. Leave the indefinite lock in place until the deadline and the disposition checks below are satisfied. Key rotation must not make a retained archive undecryptable.
- An unfinished, interrupted, failed or unverified archive has no start time for this retention period. Keep its objects, key version, source replay chunks and source fence intact until a separately reviewed reconciliation determines the correct continuation or disposition. A timeout, missing acknowledgement, or local test result does not permit cleanup.
- After the minimum period, a designated archive administrator may plan disposition only when the durable move and archive records agree, an independent restore and integrity verification have passed, no recovery, PITR, audit or investigation hold applies, and every affected key-dependent archive is accounted for. Verify the exact synthetic account, bucket, prefix and key version again before any disposition. This policy does not authorize deleting existing Woven resources or retained source data.

## Rehearsal and evidence

1. Record the run ID, identities and actual failure domains, UTC times, synthetic resource inventory, key version, effective lock and grants. Do not record key material, plaintext chunks, credentials, or sensitive project records. Verify the archive store and key custody independently before uploading; failure leaves the run fenced and the archive gate open.
2. With the actual archive writer, upload the frozen synthetic project's bounded encrypted records using conditional creation. Retain an independently authenticated commitment binding the project ID, origin, source object and generation, move ID, schema and ownership manifest, chunk count and final chain digest. Verify every uploaded object's exact read-back and a complete authenticated final seal; missing, conflicting, duplicated, reordered or cross-move records fail closed.
3. Recreate the recovery environment using only its independent credentials. Recover the synthetic key version and restore to a fresh inaccessible owner. Require matching schema, project ID, users, credentials, historical audit digests, counts, canonical per-table digests and foreign-key checks; exercise login, active and revoked sessions and a pending handoff while another synthetic project continues isolated traffic. Capture interruption, lost acknowledgement, restart and retry evidence, as well as missing object, changed ciphertext or metadata, wrong key and unauthorized access failures.
4. Record the independent seal-verification time and the resulting UTC minimum-retention deadline. Confirm that all archive objects, the seal, the independent commitment and the key version remain recoverable until at least that deadline, and retain the source fence and replay chunks throughout. Record storage, key access, lock configuration, failures and any shared failure-domain limitations without logging secret material.

Passing a local object-write test or recording this policy is not a hosted archive, custody, retention or restore proof. The writer, format, independently controlled storage and escrow, trusted commitment, actual access controls, and full restore are not yet established. Complete all other Phase 1 gates and obtain the separate explicit real-cutover authorization before touching the real singleton.
