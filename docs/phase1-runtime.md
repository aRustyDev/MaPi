# Phase 1 runtime measurement

`npm run build:phase1-owner` builds the flow, issuer and management Go dependency graphs into `worker/generated/phase1-owner.wasm`. The build uses the pinned Nextgen archive and writes an ignored manifest containing the source revision, dirty status, toolchain, tags, routes, size and SHA-256. Run `npm run baseline` and `npm run build:login-assets` before bundling. `wrangler.phase1-local.jsonc` is a local configuration with a separate namespace. Its management ingress is enabled for testing.

Run `npx wrangler deploy --config wrangler.phase1-local.jsonc --dry-run --outdir /tmp/mapi-phase1-bundle` to measure the entire uncompressed bundle. Obtain platform startup validation using a newly created isolated Worker and record its version and namespace. The dry run alone does not measure startup.

The respective dry-run configs were `wrangler.mvp.jsonc` (top-level environment), `wrangler.oidc-local.jsonc`, `wrangler.management.jsonc` and `wrangler.combined-owner.jsonc`. The copied implementation was dirty, `node_modules` was symlinked and the isolated Nextgen clone shared Git objects; this was not a clean, dependency-frozen build. No hosted startup, load, limit or memory evidence is established by these dry runs.

On November 23, 2026, the flow control also completed a disposable local run of `node scripts/benchmark-flow.mjs`, targeting a synthetic project on a loopback Wrangler listener. After one initial journey, 20 journeys ran at concurrency four: sign-in median was 1,136.62 ms and p95 was 1,163.23 ms; full journey p95 was 1,234.10 ms. The reported Wasm memory was 105,381,888 bytes at the sampled point, not a high-water mark or total isolate memory. This direct flow-request control used the dirty copied source and shared dependencies above. The initial journey followed setup and is not a confirmed cold start. The run did not use a browser, independent RP, second project, concurrent management activity or hosted platform metrics. The local listener and Wrangler's local mode did not enforce an outbound network restriction. It does not satisfy or waive any hosted runtime gate. The disposable runner's interruption and descendant cleanup has not been verified and should not be reused as an operational harness.

`npm run benchmark:phase1` is currently blocked by an unconditional provenance guard before hosted requests or setup. `phase1-benchmark-inventory.md` describes the read-only diagnostic and the proof still needed; do not bypass the guard. Once the benchmark-specific proof is implemented, `MAPI_PHASE1_FILE` names a private JSON file containing exactly two synthetic project records with `origin`, `operator`, `userFile`, `managementToken`, `userId`, and `projectId`. Restrict file permissions and bind both origins to the same isolated owner. Each child configures a temporary independent RP and uses the official browser component. Two projects run five synchronized waves of four journeys, once without management and again after a fresh throttle window with four sequential management reads per project per wave and one operator create in waves two and four. The created user is fetched through the management handler. The resulting JSON includes p95, per-request timings, per-project attempted and completed counts and throughput, errors, replay counts and final Wasm memory. Per-project and aggregate throughput use the same phase-wall interval, including local checkpoint writes.

The runner reports `trafficPass` separately from `phase1Pass`. It recomputes `trafficPass` from the two projects' retained journey, wave, management and overlap evidence and requires 22 replay attempts and rejections per project (first, warm-up and 20 measured journeys). Contradictory or malformed failure categories fail the traffic check. This is a consistency check on runner and child observations, not independent hosted or artifact attestation. The runner cannot yet validate cold-instance confirmation, artifact size and startup, platform limit errors, or isolate-memory coverage; consequently `phase1Pass` stays false and the command exits nonzero even if both traffic phases pass. This is not a replacement for collecting and reviewing those missing results, and it does not change the candidate-specific latency or sampled-memory acceptance already recorded for an earlier version.

The child now retains each full RP completion time alongside its sign-in sample. The parent rejects a missing or invalid completion sample, a completion shorter than its paired sign-in, or a reported completion p95 that differs from the 19th sorted sample. The same ordering is required for the first and warm-up journey. `node scripts/test-phase1-benchmark-latency.mjs` and `node scripts/test-phase1-benchmark-report.mjs` pass these local checks. Both measurements still originate in the child, and the corrected harness has not run in hosted Woven; this does not independently attest timing or close a runtime gate.

Each child acknowledges a wave only after all four primary-page `/start` requests have actually started. Both plain and mixed waves require all four client-observed sign-in intervals to share a nonempty overlap. The parent then runs management activity. Client-observed sign-in and management intervals, with conservative clock-offset bounds from the IPC round trip, must show that every planned get, query and create overlaps a sign-in for the same project and wave. These intervals establish client request overlap, not simultaneous execution within Workers; report server-side timing and its coverage separately. The sign-in start-to-callback and completed-journey timing boundaries remain unchanged.

The first reported journey occurs after client setup and has not been proven cold. The report explicitly lists cold-instance confirmation, platform CPU, memory and overload outcomes, and upload and startup validation as pending evidence; a mixed workload cannot pass without creation-audit verification. A passing latency result is not Phase 1 sign-off. Collect those measurements for the corresponding UTC intervals and Worker versions before applying the full runtime gate. Neither credentials nor user records belong in the report.

## Isolated startup measurement

On November 19, 2026, the production-tagged Phase 1 owner was uploaded as the newly named Woven Worker `mapi-phase1-startup-6a487d44b191`, version `fec62cce-cc9c-4ca6-b852-eb049a05ffec`. Wrangler reported 54,800.96 KiB uncompressed and 138 ms startup validation. The 55,988,313-byte Wasm had SHA-256 `a393f6cbca10eacfcefac2b03eea28ffe112bc2476270d1a9239287943d6414a`; it was built from MaPi `12555ef02d60d5ee76f328319dc988db75fc6833` plus the Phase 1 working changes. The configuration has no deployed route, no project data, and no application secrets. The result establishes the upload and startup budgets for that artifact. It does not establish hosted runtime, project isolation, or the load gates.

The generated Phase 1 owner includes `phase1Control`, an RPC method guarded by a separate control secret and the owner generation fence. `worker/phase1-control.js` uses a service binding and external Durable Object bindings, validates the operator bearer token, resolves the origin in the registry, and returns a project token or the count of `user.created` events for a specified user. `wrangler.phase1-control-local.jsonc` declares no public route and is a local binding example. Neither control operation is mounted in the owner HTTP entry point. Provisioning responses remain unchanged. Run `node scripts/test-phase1-control.mjs` for authorization and route rejection checks.

This control path is not ready for hosted use. The production owner must first initialize and enforce its fence, and a private benchmark caller must invoke the control service binding without publishing credential or audit results through an HTTP ingress. The Node benchmark can use a loopback-only caller Worker through `MAPI_PHASE1_CONTROL_URL`, which must be an HTTP URL on localhost or 127.0.0.1. The caller forwards to the private `PHASE1_CONTROL` service binding. Start it with `wrangler.phase1-caller-local.jsonc` and a loopback listener after the control and owner are available. The benchmark obtains project credentials before measurement and requires exactly one creation audit for each measured user. The caller configuration has no public route and must not be deployed as an HTTP endpoint. The local `node scripts/test-phase1-control-e2e.mjs` test exercises the real Go token and audit RPC after installing a synthetic fence, then verifies a frozen owner rejects the control call. The local test uses the real registry and owner objects, with a synthetic fence installed after provisioning. The single-process test simulates the service binding. `node scripts/test-phase1-bindings.mjs` also starts the caller, control and owner as three local Wrangler processes and verifies the service binding and external Durable Object bindings against the real registry and Go owner. Both tests install a synthetic fence and do not establish production route and fence integration. Never deploy the private control or include its RPC in an owner deployment until both the control caller and the fence are exercised end to end in an isolated environment.

Set `MAPI_RUNTIME_DIAGNOSTICS=1` for the isolated owner to emit structured Worker boot, owner boot, and reactor-ready markers. The operator status reports the owner boot ID, initialization count, Wasm high-water bytes and 64 KiB pages for that object instance. Memory is sampled at Go reactor call boundaries, including failed calls, and resets on object eviction. A fresh boot marker before the first journey is required to classify that journey as cold. Worker and owner markers do not measure total isolate memory.

Capture `wrangler tail --format=json` privately for the isolated Worker throughout both runs, then run `node scripts/summarize-phase1-tail.mjs /path/to/private-tail.jsonl`. Its output keeps only invocation CPU and wall time, outcomes and allowed diagnostic markers. Overload exceptions caught at application and management ingress log only a classification and component. Keep the raw tail private. Trace completeness must be established independently.

For periodic analytics, set `CLOUDFLARE_ACCOUNT_ID` and a read-only `CLOUDFLARE_API_TOKEN`, then run `node scripts/collect-phase1-analytics.mjs START_UTC END_UTC NAMESPACE_ID OBJECT_ID...`. The script introspects filter support and queries each object for sampled CPU, CPU/memory-limit errors, maximum sampled isolate memory, invocation status and request/error counts. It prints aggregates and labels completeness unverified. Re-run it after the platform's reporting delay. A failed query, missing samples, or absent tail coverage leaves the relevant gate unverified. The collector has not been validated against a hosted account.
