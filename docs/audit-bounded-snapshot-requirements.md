# Bounded audit snapshot: unresolved implementation boundary

This is a source-derived contract, not an implemented snapshot, a parity result, or a hosted acceptance. The temporary event split's owner still materializes a full response and its serializer has a diagnostic 12 MiB call cap. The user chose to continue toward a bounded snapshot preserving the existing behavior. The separate wire-only normalization observation was aborted before dispatch; the user chose to leave that evidence open while other work continues.

In pinned Nextgen, `EventService.List` checks visibility and returns a complete `[]*domain.Event`. SQLite `eventStatements.ListEvents` calls `collectRows` on full event rows. `events.ListEach` collects a page for every unique indexed filter value before sorting and truncating the merged events. For unindexed filters, `eventStatements.ScanEvents` collects ID, timestamp and match metadata, and `events.ScanEach` applies its 1,000-row budget per unique range. It selects the earliest range cut in page order, sorts matching metadata, derives the cursor, then fetches and reorders the selected full events. That fetch tolerates a retention purge between scan and fetch. Chunking the final serialized page after `EventService.List` returns therefore does not bound the owner-side payload materialization.

The pinned service caps a page at 100 events, not at a total byte size. Cloudflare documents an 8 MB maximum for a Durable Object SQLite string, BLOB or table row. A count limit therefore does not make a full page or even repeated copies of one large event safe within a Worker isolate. [Durable Object SQL limits](https://developers.cloudflare.com/durable-objects/platform/limits/#sql-storage-limits)

An actual replacement needs to preserve the pinned authorization and visibility decisions, input and error precedence, filter semantics, unique-range merge, ascending and descending `(created_at, id)` ordering, settled-before restriction, scan-budget cut and short/empty-page cursor, retention behavior and page token. It must preserve the original payload bytes needed by the existing loss guard and validate all application-level response data before sending a success response. The upstream encoder validates before its 200 header; like any network response, its later write can still be interrupted by a transport failure.

To bound payload memory without trusting a later requery, a candidate design needs a private, inaccessible staged snapshot or equivalent. It must bind the authenticated principal, project, route generation, request and exact selected rows to a consistent authority decision; use bounded reads and storage frames; preserve the policy's concurrency, revocation and retention semantics; and prevent publication after a fence or recovery change. It also needs a complete authenticated inventory, failure and retry rules, expiry and safe cleanup. A temporary diagnostic export, raw response string or separate ingress alone supplies none of those guarantees. Any spool is sensitive project data and must have appropriate access and retention controls.

Before adoption, compare actual Go handlers against the pinned behavior for indexed and unindexed filters, ties, both directions, scan-budget cuts, empty and partial pages, purges, visibility and authorization. Exercise large and malformed payloads, interrupted staging and serialization, duplicate or missing frames, stale route and recovery eras, concurrent revocation and freeze, cleanup, and owner eviction. Measure both complete Workers' upload/startup and hosted memory, CPU, errors and load. Do not invoke or recreate the separately interrupted bridge-cursor, real-owner, hosted or normalization-observation actions as substitutes for this work.

## Multi-invocation consistency and authority

The event table can be purged by `DeleteEventsOlderThan`; its `(project_id, id)` key alone cannot reconstruct an event deleted between snapshot steps. A high-water mark can exclude later inserts only if all writers obey the assumed version rule, and does not recover deleted or changed data. Reading different ranges over multiple invocations can also combine rows that never existed together. The current upstream `ListEach` and `ScanEach` issue separate reads, however, so their permitted interleavings are not automatically identical to one atomic snapshot. The replacement must demonstrate a permitted ordering for each query path, including `ScanEach`'s intentional purge between its scan and fetch; it must not claim atomic equivalence from a watermark alone.

An implementation can instead retain immutable row versions (including deleted versions) while a durable snapshot references them, or install a crash-safe owner write and retention fence until a protected snapshot is staged. A third possibility is to atomically copy all fields needed for each consistent upstream read into protected storage, including rows whose validation can fail even if they are later discarded; that copy itself needs bounded resource and interleaving evidence. All approaches need quota, interruption, recovery-era and cleanup rules. Merely fragmenting a read after it occurs does not preserve a deleted source row.

The authorization decision needs an explicit linearization point. One candidate is to check the actual caller, `requireProjectAccess`, project claim visibility and the server-resolved route/recovery generation as part of establishing the protected snapshot, then keep its capability private and scoped to that request, project, principal, generation and snapshot. A revocation committed before admission must deny it. A revocation afterward may be ordered after that admitted read only if the resulting behavior is shown equivalent to the pinned handler; a stricter later recheck can change the response and needs its own documented contract. Serializer and resumed jobs must not gain a reusable public capability or publish after a move or recovery invalidates the snapshot. This is a design requirement, not an implemented authorization or an expiry-clock guarantee.
