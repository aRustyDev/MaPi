# Benchmark inventory prototype

This is a read-only prototype for the separately bound benchmark control. It is not authorization to run the benchmark, provision projects, deploy a Worker, or move the real singleton. The benchmark runner has a separate unconditional fail-closed guard and is not wired to this prototype. Do not enable hosted runs until the scope, caller and deployed-version checks below are resolved.

The verifier expects a private generated directory containing `manifest.json`, `owner-frozen.json`, `router.json`, `control.json`, and `caller.json`. It validates generated names, exact HTTPS workers.dev origins, flags, logging, owner classes, the two control bindings to the owner, the router service and the local caller's remote binding. `CLOUDFLARE_ACCOUNT_ID` and a read-only `CLOUDFLARE_API_TOKEN` are supplied to the process without printing either secret. `node scripts/phase1-benchmark-inventory.mjs <directory> before` queries paginated inventories and writes `benchmark-provenance-before.json` in mode 0600. The report explicitly records account inventory scope as `unknown`: absence from token-visible pages does not prove absence from the whole account.

Cloudflare Script Search can return its rows without a pagination object.
In that case, the verifier requires an exact, unambiguous match of Worker ID
and script name against the paginated List Workers endpoint. It retains the
search rows so service and environment aliases still participate in collision
checks. The live read-only Woven check matched 56 identities across the two
endpoints. Disagreement or incomplete pagination fails closed. The match
describes token-visible resources and leaves the account-wide scope gate
unverified. See the [Script Search API](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/methods/search/)
and [List Workers API](https://developers.cloudflare.com/api/resources/workers/subresources/beta/subresources/workers/methods/list/).

The postflight checker is designed to validate approved 100%-active versions, script etags, namespace IDs and bindings, ingress subdomains, control privacy, flags, logs and module hashes. The current collector explicitly reports zone and domain scopes as `unknown`, with `zonesComplete: false` and `domainsComplete: false`; no implemented independent check can establish that the token can see every account zone or Worker domain. Both preflight and postflight explicitly record account-wide script and namespace scope as `unknown`; neither can establish complete visibility from the token alone. Consequently an `after` check with reports produced by this prototype fails closed. Do not manually change those fields to bypass the guard. Independently verified account-wide scope is required before treating either inventory as complete.

The intended `benchmark-approved.json` contains `owner`, `router` and `control` objects, each with `versionId`, `etag`, absolute `moduleDirectory`, a `modules` mapping from exact deployed module names to SHA-256 hashes, a `moduleTypes` mapping with the exact reviewed content type for every module, and `mainModule` naming the reviewed JavaScript entrypoint in that mapping. Owner modules must include JavaScript and Wasm; router and control must include JavaScript. `callerLocalSha256` is the reviewed hash of `caller.json`'s local main script. Module hashes and an etag are distinct observations; an etag is not assumed to equal a module digest. JSON files and API responses are bounded and parsing errors are sanitized. Local artifacts are hashed in bounded streaming reads with sanitized file errors, and raw script downloads are bounded to 60 MiB. The collector rejects incomplete page metadata, but consistent pages alone cannot prove an atomic snapshot if the account changes during collection.

The legacy script-content download is script-scoped. The postflight prototype instead uses the documented [beta exact-version endpoint](https://developers.cloudflare.com/api/typescript/resources/workers/subresources/beta/subresources/workers/subresources/versions/methods/get/) with `include=modules` and checks the returned module bytes, exact content types, and `main_module` for each approved version ID against reviewed metadata. Missing or mismatched metadata fails closed; no type or entrypoint is inferred. For each of owner, router and control, the approved `mainModule` must equal the basename of its configuration's `main`, and the configured local file must hash to that approved entrypoint digest. When Wrangler bundles the router or control, the configured source `main` can differ in name or bytes from the deployed entrypoint; this check then fails closed. Use reviewed deployment output with `no_bundle` when appropriate, or separately establish and review an equivalent build-to-deployment proof before using a different design. Responses may contain sensitive metadata: they are bounded and reduced to hashes, content types, and entrypoint names without logging or persisting raw response bodies. Woven's immutable-version endpoint returned Wasm names with and without a leading
`./` for different uploaded artifacts. The verifier accepts either form, maps
it to a single safe local filename, and compares the exact deployed name
against the reviewed manifest. It rejects traversal, nested paths, and
ambiguous duplicates such as `a.wasm` and `./a.wasm` in one version.

A read-only Woven check found an accepted account-wide administrator policy for
the current Wrangler identity. The API returned 56 Worker identities and 31
Durable Object namespaces before the isolated rehearsal. It listed five zones,
all with zero standard Worker routes, and five Worker custom domains.
This identifies the membership's account-wide grant and the resources visible
to the current credential. Automatic verification of effective full scope for
the benchmark's separate read-only credential remains outstanding. A matching version observation and deployment listing are point-in-time observations, not proof of global propagation or a live caller identity. Config hashes also do not establish which process is actually listening on the local control port. The prototype's `requireBenchmarkProof` therefore always fails after its input checks. A future implementation must independently establish full account scope, validate version-specific artifact identity against live responses, and start or otherwise attest the exact reviewed local caller and remote binding before allowing any writes. Account state may change immediately after any inventory, and namespace observations do not prove all prior writers drained. Static asset bytes, platform startup, CPU, memory and load evidence are separate checks.

The version response has a 96 MiB input limit and a 60 MiB total decoded-module limit. These bounds do not bound peak Node memory: parsing and decoding may hold multiple copies. They are not Durable Object isolate-memory measurements.

A local-only Wrangler probe confirmed that `--port 0` can select a loopback port for a caller launched by the harness. A port or configuration hash alone does not authenticate the listener; a future launcher must bind its verification to the reviewed child process and fail if that process exits or restarts. Wrangler's `--local` mode also disables remote bindings, so that probe does not validate the hosted private-control path. Cloudflare documents that [version overrides](https://developers.cloudflare.com/workers/versions-and-deployments/version-overrides/) can be ignored and do not apply to RPC service-binding calls. Any use of an override would therefore require a check at the actual target before mutation, and the Durable Object owner path still needs independent writer-version and rollout evidence. These observations do not open the benchmark guard.

Run `node scripts/test-phase1-benchmark-inventory.mjs` for the mocked validation and collector checks. No live API inventory, hosted validation or deployment is established by these tests.

Run `node scripts/test-phase1-version-modules.mjs` for mocked version-specific response and bound checks.

`node scripts/test-phase1-benchmark-provenance.mjs` also runs the actual paired and standalone/child hosted entry points under a local side-effect blocker. With syntactically valid synthetic settings, it verifies that the unconditional guard rejects before token or network requests, child/browser launches, RP temporary-directory creation, report writes, or standalone fixture reads. The test prevents those operations rather than contacting a service; it does not validate a live caller, account visibility, deployed artifacts, or Cloudflare behavior.
