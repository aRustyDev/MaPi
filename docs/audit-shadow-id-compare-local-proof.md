# Bounded shadow ID comparison diagnostic

The unmounted `experiments/audit-snapshot/shadow-id-compare.mjs` compares two scoped event ID byte sequences in lexicographic order using at most 32 KiB per returned SQLite fragment. It accepts signed 64-bit row handles as canonical decimal strings, avoiding JavaScript numeric rounding, requires the requested project on both rows, and copies a fragment before the next SQLite query. It is a component for a possible external handle sort, not an integrated snapshot or authorized API.

`node experiments/audit-snapshot/shadow-id-compare-native-test.mjs` passed in a disposable in-memory native SQLite database. It compared valid Unicode TEXT, BLOB, equal byte sequences of different SQLite storage types, IDs sharing a 70,000-byte prefix, signed 64-bit row-handle extrema, invalid handles and a foreign-project lookup against JavaScript byte ordering. The maximum observed returned fragment was 32,768 bytes. The test did not exercise malformed TEXT, exact platform limits, the pending handler, or the interrupted row-transfer test.

The caller must hold a synchronous stable snapshot transaction and separately enforce route, recovery era, project and reader authorization. The helper compares IDs only; timestamp conversion, full pinned Go ordering, tie permutation, authorization, retention semantics, selection, retries and output verification remain unimplemented. SQLite may materialize data or scan the view internally; neither total memory nor CPU is bounded by this fragment size. Native byte ordering is not proof of Workerd host conversion or pinned Go comparator parity, especially for malformed SQLite TEXT. No Workerd or hosted test was run and no Woven deployment was touched.
