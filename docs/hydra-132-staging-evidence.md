# Hydra integration staging evidence

This is development evidence for [#132](https://github.com/aRustyDev/MaPi/issues/132), not production release approval. The implementation is still a draft. The adoption decision and remaining release gates are in [the Hydra decision](hydra-adoption-decision.md).

## Staging setup

On 2026-11-28, the isolated staging project used the pinned Hydra OSS v26.2.0 source at `0b84568fffccf151dc5e6c7955fdfb738555bf4b`, Go 1.26.9, Binaryen 133 and Workers compatibility date `2026-11-25`. The private Hydra Worker `mapi-hydra-132-engine` was bound to `mapi-hydra-132-nextgen` through named private service entrypoints. Its Hyperdrive configuration `mapi-hydra-132-neon` had SQL caching disabled and used a dedicated Neon PostgreSQL database. The Hydra migration ran separately using a distinct migration role; the runtime role received DML privileges on the isolated schema and no migration credentials. Hyperdrive uses its default TLS mode; an attempt to configure `verify-full` without a custom CA was rejected. Do not assume that attempt established hostname verification.

The Hydra build uses `scripts/build-hydra.sh` with a checkout containing the pinned `v26.2.0` tag and `MAPI_HYDRA_WASM_OPT` pointing to Binaryen 133. The staging upload measured 64,299.62 KiB uncompressed and 13,115.40 KiB gzip, exceeding the 55 MiB uncompressed release target. The restored Hydra version was `4882eb59-a3d5-41eb-8247-011aa50e5994`; the ingress version was `41917e04-d4f9-49c4-b72f-51f2bbc2900b`. The Hydra source pin, toolchain, patch seams and adapter are retained in `experiments/hydra-phase0/build.sh` and the associated sources; example app and engine configurations are alongside them. Bootstrap the app and synthetic project first, use separate migration and runtime roles, apply Hydra's migrations and `bound-schema.sql`, disable Hyperdrive caching, register an isolated RP, and then bind the two Workers using those configurations. The synthetic user, RP client credentials, system secret and PostgreSQL credentials were generated for staging and are excluded from this repository.

## Verified behavior

The public issuer is mounted under the Nextgen project path. A hosted independent relying party completed official Nextgen login, an explicit consent screen, S256 authorization-code exchange, ID-token signature and claims checks, refresh, logout denial and code-replay denial. The runtime validates the project, subject and session against the active Nextgen owner before binding a code and before releasing a token. The authorization-code and refresh paths also use the grant fence. Hydra client-credentials and other unbound grant types are disabled in this integration.

Before the passing runs, two hosted attempts reached the callback but failed RP assertions; one returned no authorization code, and another had an insufficiently labeled assertion. Their causes were not established. The later passing runs do not explain those failures or establish reliability under load.

A separate hosted test temporarily replaced the private session-authority binding with a synthetic service that throws. Refresh returned HTTP 500 without token material. After the real authority was restored, the same refresh token succeeded; the test removed its temporary copy. This demonstrates the tested unavailable-authority schedule, not every failure or race schedule.

The disposable local PostgreSQL probe `MAPI_HYDRA_BOUND_PROBE=1 MAPI_HYDRA_SKIP_BASIC_PROBE=1 experiments/hydra-phase0/probe-local-postgres.sh <native-hydra> <build-dir>` exercised the path-based issuer, discovery, real Hydra challenge handlers, rejection of a mismatched subject, verified binding, code exchange, refresh, replay denial and a simulated unavailable session. Its session fence is a test double and it runs the Wasm adapter in Node; it does not replace hosted Durable Object race tests. An earlier local workerd/PostgreSQL run passed discovery and synthetic client-credentials issuance; a later cold workerd run timed out at the 12-second request deadline and returned HTTP 500. That startup behavior remains unresolved.

## Credential handling and remaining gates

The browser session cookie is passed transiently to the existing Nextgen session API; the adapter does not persist the raw cookie. Custom grant identity and fence state contain project, subject, session and grant references, issuer, attempt outcomes and cleanup status. Hydra's own OAuth tables still contain the protocol state it needs. Application-emitted diagnostics in the integration contain status and stage rather than credentials. Platform request-log handling and retention must also be verified before release.

The `/logout` path closes the fence before revoking the Nextgen session. Other session-revocation entrypoints are not yet proven to close it, and the release ordering and cleanup race matrix must be repeated against this adapter. Hosted transaction rollback and cancellation, two-project isolation, complete discovery and protocol profile, observability, recovery, and the size and runtime targets remain open. Do not enable this integration for production or close #132 on the basis of this staging journey alone.
