# Recovery credential boundary and proposed reopen policy

Status: **reopening is not yet safe and remains disabled**. This is a recovery policy and local proof, not an issuer-conformance claim or authorization to rotate keys or change Woven credentials. Point-in-time recovery may restore credential records or replay state that were revoked after the bookmark. Independent registry and epoch state must remain outside the restored project object.

## Evidence from the pinned code and local tests

- Current Go `GenerateJWE` persists a token record and assigns its TokenID before encoding it. `IntrospectToken` checks the stored record for ordinary revocable tokens, but explicitly accepts a revocable payload with an empty TokenID without a record lookup. See `internal/service/token.go` and `internal/storage/dialect/sqlite/token.go` in the pinned Nextgen source. The test-only `mapi_recovery_token_proof` build tag is excluded from normal builds.
- `node scripts/test-recovery-credential-proof.mjs` builds an isolated test-tagged Wasm module from the pinned source. In disposable local objects it mints a JTI-backed PAT and project token, revokes them, reinserts their saved rows to simulate a snapshot rewind, and confirms both become valid again. The local-only invalidator removes stored token rows through the Go token service in bounded audited transactions; both credentials then fail introspection, the other project's token remains valid, and an injected audit failure rolls the transaction back. Typed legacy PAT, project, preview, session, OIDC-access and SAML-assertion JWEs without a TokenID work at epoch `0`. The owner token-service wrapper rejects these revocable no-TokenID credentials at a nonzero recovery epoch, rejects missing, foreign or ambiguous owner authority, and allows a newly issued JTI-backed project credential. The real Go project-bearer and session-cookie handlers are exercised before and after the simulated epoch change; OIDC and SAML coverage is direct real-Go token-service introspection, not issuer-protocol coverage. Legacy session, OIDC and SAML credentials in an independently provisioned second project remain valid at its unchanged epoch. This is a local simulation, not PITR or permission to reopen.
- The bearer code and refresh exchanges and online access validation re-read the live session, so a deleted session blocks those online paths. `TokenIssuer.Access` also consults revocation and client epoch state. See `upstream/overlay/apps/api/internal/mapioauth/provider.go` and `tokens.go`; FAPI is a separate private experimental surface and must be inventoried independently.
- `node scripts/test-recovery-offline-jwt.mjs` runs a pinned native recovery-specific test with synthetic keys. After session revocation, online access validation rejects the access token while an offline verifier using a cached public key still verifies both access and ID JWTs. Ordinary signing-key rotation retains the retired public key in JWKS and does not change this result. The current bearer composition uses a five-minute lifetime, but the implementation permits other values; deployed historical lifetimes, verifier clock leeway, key-cache retention and relying-party sessions are not established by that fixture. See `compose.go`, `tokens.go` and `signing.go`.
- Issuer signing private keys are wrapped with the project's token-purpose encryption key. Removing or rotating that key without a verified rewrapping or replacement process can make signing keys unreadable. A stored-key change also cannot erase public keys already cached by an offline relying party.

## Proposed fail-closed reopen policy

1. **Keep the affected route and direct owner calls closed.** Reserve the recovery in the independent registry, finish or reject any move, freeze the owner, capture the aggregate and complete per-scope revision high-water, deploy a fresh epoch map retaining every previously guarded owner, and independently verify version adoption and old-instance/in-flight drain. Verify and retain the backup, bookmark, immutable deployment identifiers and recovery journal. An environment flag alone is not drain evidence.
2. **Inventory credentials and consumers before recovery.** Identify the actual issuer profiles, project and personal tokens, legacy no-TokenID credentials, applications and client authentication methods, signing and encryption key IDs, RP token-validation modes, maximum issued lifetimes, clock leeway, JWKS cache policies and downstream application sessions. Include client assertion/replay records, DPoP state, code and refresh families, client-secret hashes and client epochs. If the inventory or a relevant lifetime is unknown, the route stays closed until that risk has an explicit, reviewed disposition.
3. **Restore and reconcile under the fence.** Only after Cloudflare PITR semantics, independent registry recovery, old-code drain and recovery-era deployment are proven may an executor schedule a restore. Verify object/project identity, schema and ownership, restore each captured scope to at least its independent high-water, reconcile the restored state and preserve audit evidence. Reset the staging checkpoint only through a separately audited and fenced protocol; no such reset or production restore executor exists yet.
4. **Invalidate online credentials and replace secrets deliberately.** Run an independently reviewed, restartable and audited invalidation that removes all pre-recovery auth attempts and challenges, revokes sessions, handoffs and all restored token records, and accounts for credentials generated after the bookmark. The current token-row cleanup is local-only; the completed singleton checkpoint has no safe archive transition for a later era. Require all old PATs and project credentials to be replaced, and reconcile or reissue affected client secrets and other application credentials from an authority that was not rewound. Keep audit and checkpoint evidence for each batch; do not expose new credentials in logs.
5. **Close the legacy no-TokenID path.** Before reopen, verify the nonzero owner epoch is independently anchored and retained across deployment, eviction and PITR. The new local wrapper rejects revocable no-TokenID credentials after that transition, but has not yet been proven across all relevant ingress and verifier paths. Deleting token rows alone is insufficient. The wrapper intentionally does not reject non-revocable flow and JWT-profile payloads; reconcile those and issuer client/assertion state separately, or establish an independently reviewed key-replacement and rewrapping procedure with equivalent negative tests.
6. **Account for offline JWTs and downstream sessions.** Each affected RP must either enforce an independently checked recovery-era/online-validation policy and invalidate its downstream sessions, or participate in a verified expiration and cache-retirement window derived from actual issued credentials, clocks, key caches and session behavior. A normal key rotation or owner-side revocation is not by itself proof of offline invalidation. A relying party with unknown validation, unknown maximum token lifetime, an unbounded downstream session, or no coordinated invalidation prevents an unconditional safe reopen.
7. **Reopen only after independent verification.** Complete session, handoff, attempt, token and issuer/client checks; verify required reissued credentials and RP controls; install and verify the new epoch and higher generation on the owner; then use a registry CAS that independently checks the owner and evidence. Verify stale direct RPCs, restored credentials, pre-recovery challenges and other-project isolation after restart. An explicit cutover authorization is still required. If any step is interrupted, the owner stays fenced and the route stays recovering; repair forward from durable checkpoints.

## Remaining local tests before a production candidate

- Integrate the token-row invalidator with a durable, separately fenced checkpoint archive and prove a second recovery era, rollback at each audit, dropped acknowledgements and restart; then test against representative token counts and platform limits.
- Exercise legacy/no-TokenID rejection or key replacement and signing-key rewrap failure/retry against all actual ingress paths, including management, flow, issuer and any private profiles. Prove old key caches and restored keys cannot silently restore the retired authority.
- Prove client-secret, client-epoch, assertion replay, DPoP and issuer code/refresh state reconciliation against a rewind, and confirm invalid or restored grants cannot mint new tokens. Keep issuer conformance in its later phase.
- Test epoch-map retention across successive projects and independent-registry recovery; prove bounded session, attempt, credential, scope and audit recovery with interrupted PITR on isolated hosted objects. Verify RP online/offline behavior and downstream logout using actual test integrations.
- Rebuild the exact fence-aware Worker and repeat upload, startup and hosted resource/error checks. Any code changes here invalidate measurements from an older artifact.
