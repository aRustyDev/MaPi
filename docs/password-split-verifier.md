# Private split password verifier experiment

This is a design and an isolated local state-machine test, not an integrated login path. `scripts/password-split-protocol.mjs` has no public route and its test uses synthetic tables and verifier results. It is not connected to the separate Argon2 Worker spike, upstream Go handlers, or actual project credentials. There is no production-wide mutation revision or migration in MaPi yet.

## Pinned behavior

At Nextgen commit `b0b74cd4a198428ea9b82910c217259ffc62b65c`, `authAttemptService.VerifyProof` reads the attempt and invokes `verify` before the success transaction. `PreparePasswordVerification` requires an unexpired, not-handed-off attempt, the current password challenge and a pinned user factor. `GetUserPassword` selects the newest password row for that project/user, by `created_at`. The project hasher verifies the password and may return an updated hash; a hash-policy resolution failure falls back to the default verify-only provider. A matching password whose rehash fails still succeeds, and storing a rehash is best effort. A hashing-busy or interrupted operation is not recorded as an incorrect password.

On a match, `AuthAttemptChallengeSucceeded` and `auth.check.succeeded` commit together. On a wrong password or missing password row, `recordProofFailure` best-effort increments the challenge's failure count and writes `auth.check.failed` in one transaction; failure to record does not override the rejection. The tagged SQLite success and failure updates match project, attempt, check type and ID. They do not by themselves re-read attempt expiry, current credential, user status or step-up session, and the success update does not require `last_challenged_at IS NOT NULL`. Therefore an await between preparation and commit needs additional fencing; the prototype must not treat the verification boolean as authority to write a factor.

## Required boundary

1. In the project object's `transactionSync`, use upstream domain preparation and read the authoritative attempt, current password challenge, pinned user factor and current password row. Capture the exact credential ID and hash, project/user/attempt/challenge IDs, challenge generation/state, attempt expiry and handoff state, relevant flow and policy revision, and any bound session's current identity, token/revocation generation and expiry. Keep nanosecond integers exact; do not round them through JavaScript numbers. Reject incomplete or ambiguous state. Enforce the selected account-state policy and make any deviation from native behavior explicit: the pinned identifier resolver itself can resolve users of any status.
2. In the same transaction acquire a short-lived, project/attempt/challenge-scoped job. Permit only one in-flight verification per challenge. The job uses a server-created random ID and stores no plaintext password, encoded hash or verifier result. Keep the full snapshot only inside the suspended trusted invocation. Rate-limit before reserving. Expired jobs can be reclaimed, but a late result must match its own still-current job and must never delete a newer reservation.
3. Outside all SQLite transactions, send the password and hash only over a private service binding with an authenticated, strictly bounded request, supported algorithm and cost, deadline and cancellation. The test spike currently supports only one Argon2id setting; all other upstream-supported hashes and rehash behavior are gaps. Never log request or response secrets. Do not expose a finish endpoint: only the suspended object invocation may use the result from its own authenticated service call. Treat errors, malformed results, timeout, cancellation and unsupported policy as unavailable, not a password failure.
4. In a second `transactionSync`, re-read authoritative state and the job, prove the challenge remains current and unconsumed and the attempt and bound session remain valid, and compare the entire snapshot including the current credential ID/hash and a monotonic mutation revision. Only then consume the job and call upstream Go's password-factor mutation and audit in the same transaction. For a real mismatch, apply the upstream failure counter and audit together with its best-effort error behavior. A stale result does neither. A verified result with a rehash must use an exact old-hash/current-row compare-and-set and preserve upstream best-effort rehash rules; this experiment deliberately rejects all rehash results.
5. The mutation revision must advance atomically on **every** operation that can change or restore relevant credential, password policy, user status, user factor, attempt/challenge, flow or session state, including admin routes, login/step-up, direct SQL migration, restore, relocation and revoke. Comparing values or timestamps alone cannot detect an ABA change and restore. Use a non-reused generation across restore/relocation, and fence stale object routes. Until the upstream adapters have that coverage, there is no safe production integration. The conservative per-project epoch in this experiment would reject unrelated writes too; it is safe only if the coverage invariant actually holds.

An eviction or lost response cannot be resumed using a client-provided verification result. The job becomes reclaimable after its lease; a retry repeats verification. In-flight work must also be bounded for CPU, memory and request quotas. This split does not make cross-object updates atomic and does not bypass Nextgen authorization, throttling or mutation auditing.

## Local evidence

Run `node scripts/test-password-split.mjs`. It uses actual local workerd SQLite transactions, synthetic state and a controllable async verifier. It covers committed success and failure, one-time challenge consumption, concurrent reservation, unavailable/malformed/late results, failure-audit rollback, lease expiry and a late old invocation, and mutations during verification for credential changes, ABA generation, challenge replacement/consumption, handoff, user deactivation, session revocation and policy change. It does **not** exercise upstream Go statements or a real Argon2 service, make a hosted call, or prove parity; those integrations and corresponding native/workerd comparisons are required next.

## Real-upstream mutation-generation spike

`node scripts/test-mutation-generation.mjs` builds a **test-only** combined reactor and runs an instrumented SQLite Durable Object locally. Immediately after installing the pinned baseline, the experiment adds row-level `INSERT`, `UPDATE`, and `DELETE` triggers to every existing application table, excluding only its own generation/trace tables and the test's verification-job table. Each trigger increments a single SQLite integer in the same statement transaction. The generation is read as decimal text to preserve all 64 bits; at `9223372036854775807` further instrumented writes abort rather than wrap. Test-only per-table counters identify which writes fired. The broad generation intentionally permits false conflicts, including from audit writes, to avoid guessing which mutations matter.

A local run instrumented 58 baseline tables. It suspended test verifications across actual upstream project/user provisioning, flow start, challenge submissions, session exchange and deletion, password-row replacement through pinned SQLite statements, user deactivation through pinned statements, and password-policy publication through the upstream service. Each advanced the generation and invalidated the snapshot. It also checked transaction rollback does not advance the counter, an active→inactive→active ABA advances it, and integer exhaustion aborts a user write. The tested session deletion occurred inside the private FAPI app probe; the probe also performed other writes, and a per-table counter separately confirmed a `sessions` mutation. Test Wasm was 56,122,059 bytes and its linear memory was 108,003,328 bytes in one 1,261 ms local run; these are not hosted measurements.

This does **not** establish complete production instrumentation. In particular:

- The private FAPI initialization creates additional tables after the baseline triggers are installed. The test detects missing trigger names and reinstalls them while isolated. Production must fence traffic during each schema change, install and verify correct trigger *definitions* atomically before reopening, and fail closed if any newly created table is uncovered. `IF NOT EXISTS` and checking names alone are insufficient against a mismatched definition or privileged mutation of the fence itself.
- A counter inside SQLite is rewound by point-in-time restore and copied by relocation. It cannot alone distinguish two histories with the same counter. A non-reused external recovery/ownership era must come from independently authoritative control state, and every snapshot/commit must validate both era and counter. Restore must fence traffic, establish a fresh era, invalidate sessions and handoffs, and reconcile ownership before reopening. Relocation must freeze the old owner, fence all writers, activate the new owner only after a verified registry cutover, and reject stale routes. The current app, registry, and recovery path do not enforce this protocol. The test did not perform PITR or a real relocation.
- Row triggers do not cover schema DDL, tables added after installation, mutations through another storage mechanism, direct tampering with the generation row, or writes by code with privileged access that removes triggers. A complete inventory and migration/privilege design must prove those paths. The test's `split_jobs` exception is safe only while those rows never affect credential or authorization state.
- The counter is deliberately global per object. Unrelated mutations can invalidate verification, and high audit volume may cause starvation and additional SQLite writes. Measure real concurrent load, trigger billing and storage effects before choosing this scheme. A narrower per-principal revision requires equally complete dependency tracking.
- The test resumes a synthetic verifier after real upstream writes; it does not yet split or commit the actual Nextgen password verifier, prove all supported hash/rehash and error behavior, or test hosted concurrency. No production handler or deployed Worker uses these triggers.
