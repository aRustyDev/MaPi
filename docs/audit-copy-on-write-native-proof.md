# Audit copy-on-write: native SQLite mechanism experiments

These experiments are local, unmounted mechanism tests. They do not implement an authorized audit snapshot, a Worker route, a supported schema change or a deployment.

`node experiments/audit-snapshot/copy-on-write-native-test.mjs` passed against a small synthetic table. A single active snapshot used SQLite triggers to copy an original row before an UPDATE or DELETE, and before a new row could conflict with an original by rowid or unique key. Payloads were copied in 64-byte fragments, and post-snapshot rowids were tracked separately. With recursive triggers disabled, the reconstructed original view survived regular inserts, `ON CONFLICT DO NOTHING`, `INSERT OR REPLACE`, `UPDATE OR REPLACE`, a replacement conflicting with two different original rows, updates and deletes of new rows, and transaction rollback. The fixture included two project IDs and a pre-existing rowid of -1. This demonstrates the tested mechanism, not transparent production behavior.

`node experiments/audit-snapshot/copy-on-write-pinned-native-test.mjs` also passed. It creates the `events` table from the generated pinned baseline DDL and confirms that this table's implicit primary-key index is `(project_id,id)`; it does not load the rest of the baseline's indexes. Triggers copied all 25 pinned event fields inside SQLite into typed cells and at most 64 KiB fragments, without passing field contents through JavaScript during copying. The synthetic original view matched the pre-mutation storage classes and raw representations for the tested insert, no-op, replacement, update, delete, dual-conflict and rollback cases. One original BLOB was 131,073 bytes and produced three fragments; one INTEGER exceeded JavaScript's exact numeric range. This is not an exact platform-size, nonfinite, malformed-TEXT, normalization or bridge-cursor test.

The same pinned-column test used `createAuditCaptureSchema` to create the existing unmounted capture tables, then used a **test-only trusted SQL adapter** to copy a saved row's typed cells into that format. It checked cell counts, types and SQL equality, exact replay, rejection after staged-cell tampering, and rollback of an injected failure before the row marker. It did not call `captureAuditSourceRow` for a saved version, authenticate a principal, or expose a Worker API. REAL replay was excluded because SQLite numeric equality is not a bit-exact comparison.

## Conflict-policy counterexample

An independent native SQLite review found that the outer statement's `OR FAIL` or `OR ABORT` can override `INSERT OR IGNORE` inside a trigger. The COW prototype uses that inner pattern for both original-version and post-snapshot-rowid markers. In the focused synthetic test, an initial `ON CONFLICT DO NOTHING` speculatively saved the original; a subsequent otherwise-valid `UPDATE OR FAIL` or `UPDATE OR ABORT` then failed on the duplicate internal marker. Separately, after inserting a new row, an `AFTER UPDATE` marker conflict caused `UPDATE OR FAIL` to return an error even though its change remained in the database; `OR ABORT` returned an error and rolled that statement back. These cases are not covered by the preceding pinned-column experiment and disprove transparent write parity for the current trigger prototype.

The distinct command `node experiments/audit-snapshot/copy-on-write-conflict-policy-native-test.mjs` passed. In its single-connection synthetic schema, replacing both marker writes with conditional `INSERT ... SELECT ... WHERE NOT EXISTS` avoided the tested duplicate conflicts under both outer policies, preserved the originally saved value, and permitted a later replacement. The first ad hoc counterexample attempt failed before the assertion because SQL string literals were quoted as identifiers; a corrected in-memory test established the original `OR FAIL` failure before the retained test was written.

The same conditional marker writes were then applied to the **unmounted pinned-column test**. `node experiments/audit-snapshot/copy-on-write-pinned-native-test.mjs` exited 0 after a no-op conflict followed by `UPDATE OR FAIL` and `UPDATE OR ABORT` of both an original row and a newly inserted row, while still checking the earlier original-view, replacement and rollback assertions. The test-only staging adapter now compares the saved project's TEXT type and exact fragmented bytes to the route before staging. It rejects a saved foreign-project row and leaves its destination empty. Its tested project IDs fit one fragment. This remains a mechanism test, not production authorization or proof of concurrent, Workerd, schema, quota, or full event-query semantics.

## Open requirements

- The mechanism assumes one snapshot, trusted unchanged table and trigger definitions, the pinned primary key and rowid as the complete conflict set, and no other unique indexes. Actual application schema, unique indexes, triggers, schema replacement, `DROP TABLE`, restore and old-writer behavior must be checked and fenced before it can protect source state. It does not cover multiple simultaneous snapshots or prove the bridge's SQL behavior.
- A `BEFORE INSERT` check can copy a pre-existing rowid of -1 even for an ordinary automatically assigned rowid, and a conflict that becomes `DO NOTHING` can also cause a needless copy. These copies consume storage and CPU; quota or transaction failure could turn an otherwise successful business write into a failure. No quota reservation, cleanup, crash-resumable lifecycle, availability policy or failure response is implemented.
- Triggers and cell tables contain sensitive project data. Access control, encryption policy, trusted source-version identity, independent integrity authority, full-history authentication, replay after recovery and protection against an adversarial writer remain unproven. The test-only adapter's SQL equality and row count do not establish authenticated full-history integrity.
- The test-only adapter now checks the saved project's type and exact bytes against the owner route, but its integrated checks cover only small one-fragment project IDs. The separate `node experiments/audit-snapshot/copy-on-write-project-scope-native-test.mjs` checks matching, foreign, case-different, wrong-storage-type, missing and tampered single-fragment values. Neither check proves an authenticated selector, independently protected saved cells, multi-fragment project identity, Workerd, or production behavior. A writer able to alter both saved cells and their apparent identity remains outside this prototype's trust boundary.
- The reconstructed synthetic view does not implement the pinned filters, range scan, read/error order, cursor, authorization, retention interleavings, response validation, serialization or real API handlers. It is not yet a multi-request audit snapshot. SQLite internal memory, total storage/CPU, invocation duration, platform limits, Workerd behavior, Worker size and hosted traffic remain unmeasured.

No Woven or AWS resource was changed. The previously interrupted archive, exact-size, nonfinite, malformed-TEXT, cursor, normalization and hosted actions were not rerun.
