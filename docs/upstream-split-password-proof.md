# Private upstream split-password integration

This is a **local test-only** integration, not a public authentication route. It combines the pinned Nextgen Go password-attempt service and Durable Object SQLite bridge with the separate pinned Go/WASI Argon2 verifier through a private Worker service binding. Neither the verifier result nor the finish operation is accepted from a browser. The suspended owner invocation keeps the credential snapshot and password in memory; the durable job contains only identifiers, a random job ID and lease. The local harness uses synthetic project data and does not print passwords, hashes, cookies, tokens or the service secret.

After `node scripts/fixture.mjs`, reproduce with Node, the pinned Go 1.26.9 toolchain, the repository dependencies, and local loopback access:

```sh
node scripts/test-upstream-split.mjs
```

The build archives pinned Nextgen commit `b0b74cd4a198428ea9b82910c217259ffc62b65c`, applies the local overlay and audit patch in a temporary checkout, and builds both test reactors. It does not deploy either Worker. Use `GOPROXY=off` with an already-populated Go module cache for an offline build.

## How the isolated bridge works

The owner loads the actual upstream auth attempt and calls `PreparePasswordVerification`, reads the resolved user and current password row, and snapshots the credential ID and encoded hash. It requires an active user, a bounded unexpired attempt and no parent session. It rejects projects with a password-hash-policy override; the separate verifier only accepts the pinned default Argon2id profile. The host snapshots an exact decimal SQLite mutation generation and reserves one short-lived job for the challenge in the same synchronous transaction. The job table stores neither the password nor the hash.

After the transaction closes, the owner calls the private verifier, which uses upstream `domain.UserPassword.Verify` with its normal NFC normalization. The owner then reopens a synchronous transaction, checks the job, lease, expiry, upstream state and mutation generation, and invokes the original upstream `AuthAttemptService.VerifyProof` with a test-only, one-use `PasswordHasher`. That hasher checks the exact stored hash and normalized password against the private call's snapshot and supplies the verified result; a mismatched oracle context reports an operational hashing-busy error, not a wrong password. The unmodified upstream service performs the successful factor mutation and `auth.check.succeeded` audit together, or its best-effort failure counter and `auth.check.failed` audit. Only the owner invocation can call this test-only finish export.

The original service's success and failure transaction calls are nested in the owner's fencing transaction. A wrong-password result is returned as data so the outer transaction does not undo the upstream failure record. If the verifier is unavailable, times out, returns malformed output or requests a rehash, the experiment returns unavailable without recording an incorrect password. Upstream best-effort failure-accounting semantics are preserved when the failure audit itself fails. A matching result whose success audit fails rolls back the factor and permits retry.

## Evidence and limits

The local workerd test exercises a real wrong password, failure counter and audit; a correct password, handoff, session exchange, session read, revocation and cookie replay; one active job per challenge; a late old lease versus a newer reservation; success and failure audit faults; an actual private-service timeout; malformed output, unsupported hash and rehash; and a mismatched oracle context. It suspends actual verifier calls while changing the upstream password row, replacing the challenge, publishing a policy, deactivating the user, revoking a session, and performing user-state, hash and project hash-policy ABA mutations. Each stale result is rejected without a success audit. It also checks expiry with no intervening write and rejects parent-session attempts. The job row is inspected to ensure it contains neither synthetic password nor hash. A separate native Nextgen run matches the wrong-password error code and the password-to-session/read/revoke behavior; it is not a complete HTTP response, policy or audit parity suite.

One local clean-archive run built a **53,831,465-byte** owner Wasm and observed **38,273,024 bytes** of owner Wasm linear memory after the test. It started from a prehashed synthetic fixture, so provisioning did not run Argon2 inside the owner. These are not total isolate memory, startup, hosted CPU, concurrent throughput or end-to-end latency measurements. The separate verifier runs the original Argon2id settings; it can continue consuming CPU after a caller times out because an in-progress Go hash cannot be cancelled. Measure both isolates and actual service-binding queueing before drawing a capacity conclusion.

The broad SQLite trigger counter is experimental. It lacks verified trigger definitions, a production migration/privilege protocol, complete coverage for new tables or non-SQL writes, and a non-reused recovery/ownership era. PITR can rewind the counter; relocation can copy it. Do not rely on this fence for real traffic until all writers, schema changes, recovery and stale routes are covered. The test does not exercise a real restore, relocation or owner eviction during verification.

The proof intentionally fails closed for parent-session/step-up attempts, missing credentials, non-default project hash policies, alternate verifier algorithms and costs, and any returned rehash. It does not reproduce the upstream missing-password error path, full error/status contracts, hash-policy fallback and best-effort rehash behavior, unknown-account handling, authorization at public ingress, durable rate limits, or all native audit payloads. The active-user restriction is stricter than the pinned identifier resolver. Trigger-induced contention, verifier authentication and rotation, bounded response handling, distributed admission, logging, lifecycle cleanup and independent security review remain open. This must not be wired into the deployed app on the strength of this test.
