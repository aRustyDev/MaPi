# Private upstream split-password integration

This is a **local test-only** integration, not a public authentication route. It combines the pinned Nextgen Go password-attempt service and Durable Object SQLite bridge with the separate pinned Go/WASI Argon2 verifier through a private Worker service binding. Neither the verifier result nor the finish operation is accepted from a browser. The suspended owner invocation keeps the credential snapshot and password in memory; the durable job contains only identifiers, a random job ID and lease. The local harness uses synthetic project data and does not print passwords, hashes, cookies, tokens or the service secret.

After `node scripts/fixture.mjs`, reproduce with Node, the pinned Go 1.26.9 toolchain, the repository dependencies, and local loopback access:

```sh
node scripts/test-upstream-split.mjs
```

The build archives pinned Nextgen commit `b0b74cd4a198428ea9b82910c217259ffc62b65c`, applies the local overlay and audit patch in a temporary checkout, and builds both test reactors. It does not deploy either Worker. Use `GOPROXY=off` with an already-populated Go module cache for an offline build.

## How the isolated bridge works

The owner loads the actual upstream auth attempt and calls `PreparePasswordVerification`, reads the resolved user and current password row, and snapshots the credential ID and encoded hash. It requires an active user, a bounded unexpired attempt and no parent session. It rejects projects with a password-hash-policy override; the separate verifier only accepts the pinned default Argon2id profile. The host snapshots an exact decimal SQLite mutation generation and reserves one short-lived job for the challenge in the same synchronous transaction. The job table stores neither the password nor the hash.

After the transaction closes, the owner calls the private verifier, which uses upstream `domain.UserPassword.Verify` with its normal NFC normalization. The owner then reopens a synchronous transaction, checks the job, lease, expiry, upstream state and mutation generation, and invokes the original upstream `AuthAttemptService.VerifyProof` with a test-only, one-use `PasswordHasher`. That hasher checks the exact stored hash and normalized password against the private call's snapshot and supplies the verified result; a mismatched oracle context reports an operational hashing-busy error, not a wrong password. The unmodified upstream service performs the successful factor mutation and `auth.check.succeeded` audit together, or its best-effort failure counter and `auth.check.failed` audit. Only the owner invocation can call this test-only finish export.

The original service's success and failure transaction calls are nested in the owner's fencing transaction. A wrong-password result is returned as data so the outer transaction does not undo the upstream failure record. If the verifier is unavailable, times out, returns malformed output or requests a rehash, the experiment returns unavailable without recording an incorrect password. Upstream best-effort failure-accounting semantics are preserved when the failure audit itself fails. A matching result whose success audit fails rolls back the factor and permits retry.

## Evidence and limits

The local workerd test exercises a real wrong password, failure counter and audit; a correct password, handoff, session exchange, session read, revocation and cookie replay; one active job per challenge; a late old lease versus a newer reservation; success and failure audit faults; an actual private-service timeout; malformed output, unsupported hash and rehash; and a mismatched oracle context. It suspends actual verifier calls while changing the upstream password row, replacing the challenge, publishing a policy, deactivating the user, revoking a session, and performing user-state, hash and project hash-policy ABA mutations. Each stale result is rejected without a success audit. It also checks expiry with no intervening write and rejects parent-session attempts. The job row is inspected to ensure it contains neither synthetic password nor hash. A separate native Nextgen run matches the wrong-password error code and the password-to-session/read/revoke behavior; it is not a complete HTTP response, policy or audit parity suite.

One local clean-archive run built a **53,831,465-byte** owner Wasm and observed **38,273,024 bytes** of owner Wasm linear memory after the test. It started from a prehashed synthetic fixture, so provisioning did not run Argon2 inside the owner. These are not total isolate memory, startup, hosted CPU, concurrent throughput or end-to-end latency measurements. The separate verifier runs the original Argon2id settings; it can continue consuming CPU after a caller times out because an in-progress Go hash cannot be cancelled. Measure both isolates and actual service-binding queueing before drawing a capacity conclusion.

The broad SQLite trigger counter is experimental. The local authority check now compares expected trigger definitions and tracked table names, but the counter still lacks a production migration and privilege protocol, verified coverage of all non-SQL writes, and a proven non-reused recovery/ownership era. PITR can rewind the counter; relocation can copy it. Do not rely on this fence for real traffic until all writers, schema changes, recovery and stale routes are covered. The test does not exercise a real restore, relocation or owner eviction during verification.

The proof intentionally fails closed for parent-session/step-up attempts, missing credentials, non-default project hash policies, alternate verifier algorithms and costs, and any returned rehash. It does not reproduce the upstream missing-password error path, full error/status contracts, hash-policy fallback and best-effort rehash behavior, unknown-account handling, authorization at public ingress, durable rate limits, or all native audit payloads. The active-user restriction is stricter than the pinned identifier resolver. Trigger-induced contention, verifier authentication and rotation, bounded response handling, distributed admission, logging, lifecycle cleanup and independent security review remain open. This must not be wired into the deployed app on the strength of this test.

## Owner-fence and recovery-era experiment

The local-only split helper can also receive a server-owned `authority` check. It evaluates that check inside the initial SQLite transaction and again inside the final mutation transaction after the verifier service call. The updated real-Go workerd test uses `assertOwnerFence` and a recovery-era expectation, and holds a private verifier result while freezing the owner or changing its local era. Each test deliberately rewinds the experimental SQL mutation counter to the earlier value before releasing the verifier; the final owner/era check still rejects it without a success audit. The existing test also waits across a real asynchronous verifier/timer boundary until the attempt expires, with no intervening business mutation, and rejects the late proof. `MAPI_TEST_PREBUILT=1 node scripts/test-upstream-split.mjs` passed after building with `GOCACHE=/private/tmp/mapi-phase1-go-cache GOPROXY=off node scripts/build-upstream-split-test.mjs`; it also checked the native wrong-proof code and password-to-session lifecycle.

This is not enabled in the application. The test's route and expected recovery era are synthetic, and its experimental generation trigger set has not been proven complete or protected against DDL and PITR. A real integration must obtain route authority from the registry and a recovery era from an independently anchored source, validate all mutation coverage and ABA protection, and handle hash-policy overrides, step-up, rehash, authorization, throttles, and resource admission. The asynchronous boundary refreshes the platform clock at the service response, but the clock can then remain fixed during the following synchronous commit. This test does not establish a strict real-time expiry bound for an arbitrarily long commit or hosted behavior.

The local experiment now uses an unmounted `experimentalSplitAuthority` adapter. It obtains the route from the real `ProjectRegistry` before and after the verifier I/O, requires that the namespace resolves the same owner object, and checks the owner fence and an independently configured object-specific recovery epoch in the admission and finish transactions. Local tests hold the verifier while the registry marks the route moving or recovering; both results are rejected even before the owner fence changes. They also replace a generation trigger with an identically named but different trigger, or drop a tracked table, and verify that the proof is rejected. Trigger SQL and the tracked table set are compared in the local authority check. These checks do not protect against a principal that can mutate the generation bookkeeping or its authority configuration.

The prototype uses the extracted `admitLogin` calculation shared with the owner. A local test seeds the existing password IP limit, shows that a wrong proof consumes the final slot even when the proof is rejected, and confirms the next attempt never reaches the verifier. The owner fence regression test passed after the extraction. The wider `test:flow-throttle` command was not run against an application in this check because it requires a configured `MAPI_URL` and operator token. The helper remains unmounted and optional in the isolated protocol; production use must make every authority, admission and generation check mandatory, prevent callers from replacing callbacks, and validate existing schema and privilege boundaries. Changes to a throttle counter are excluded from the prototype's broad mutation generation because admission is applied separately; this does not establish complete production throttle coverage.


## Requirements before production integration

- Route all supported authentication entry points through a server-owned split coordinator; never accept a verifier result, authority callback, route, epoch or completion instruction from a browser. Re-resolve the registry after verifier I/O and validate the owner fence and independently deployed recovery era in the same transaction as the final mutation and audit. Recovery must invalidate outstanding jobs before reopening.
- Establish and protect the mutation-generation schema transactionally before accepting traffic. Verify every definition and protected table at startup and on completion, include all relevant state changes and schema upgrades, prevent privileged writes to generation bookkeeping, and test relocation, eviction, restore ABA, concurrent requests and failover. An aggregate generation can cause unrelated requests to retry and duplicate Argon2 work; measure admission, retries and capacity on both Workers.
- Wire the real owner throttle and all other existing authorization and request guards; do not permit callers to supply the prototype's optional callbacks. Implement or explicitly reject unsupported credential/hash-policy overrides, rehash, missing-user behavior, step-up/parent-session cases, and verifier failure with matching upstream error, audit and retry semantics. Compare all supported routes against native and existing Go handlers.
- Retain the real attempt, challenge, credential and policy revalidation at the final transaction, with one-use proof, durable lease, rollback, replay and audit checks. Recheck expiration after the asynchronous verifier and registry I/O. Workers can freeze the wall clock again during the subsequent synchronous commit, so prove a defensible upper bound for that commit and account for it conservatively, or obtain a trusted freshness mechanism. The current test does not prove strict wall-time expiry for an arbitrarily long synchronous commit.

The available Cloudflare clock and synchronous transaction APIs do not supply such an elapsed-time guarantee inside a single commit. Consequently this local prototype is not a complete fix for the frozen-clock expiry gap and must remain unmounted pending a bounded, reviewed design and hosted evidence.

Cloudflare's [Performance API documentation](https://developers.cloudflare.com/workers/runtime-apis/performance/) states that deployed Workers' `Date.now()` and `performance.now()` advance after I/O, rather than during uninterrupted CPU work. Its [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/) state that an HTTP or RPC invocation has no hard wall-time limit while the caller remains connected. These facts support the unresolved concern but do not by themselves establish the elapsed duration of a particular transaction. An invocation CPU-time budget is not an upper bound on real elapsed time; consequently, substituting `performance.now()`, checking a timer callback, or adding a fixed unverified safety margin does not establish commit-time expiry. A solution needs a trusted freshness check at the actual authority boundary or an independently justified upper bound covering the entire synchronous commit, including pauses, together with tests for the real owner and every affected time-based path.

The local `TestMaPiFrozenClockAfterSynchronousWork` diagnostic now exercises the actual pinned Go `AuthAttempt.IsExpired` predicate with a deliberately frozen test WASI clock. In disposable workerd runs, test-host `performance.now()` measured 42 ms and 60 ms between synchronous markers placed before the final predicate call, while the attempt's TTL was 2 ms; the predicate still returned not expired. The runner checks that the test ran, the supplied clock stayed fixed, no simulated timer poll occurred, and the local marker interval was at least 20 ms. A synthetic zero-duration host result was rejected. Reproduce with `MAPI_EXPIRY_CONTRACT=1 MAPI_FREEZE_TEST_CLOCK=1 MAPI_STMTTEST_FILTER='^TestMaPiFrozenClockAfterSynchronousWork$' node scripts/test-upstream-sqlite-wasi.mjs`. A passing test demonstrates the stale-clock counterexample, not correct expiry. The measured clock is only a local diagnostic; hosted Workers can freeze `performance.now()` too, and this test neither measures a real hosted transaction nor repairs the production flow.

### Fenced reservation cleanup

The experiment's reservation cleanup now checks the original owner authority and recovery era in the same synchronous transaction before deleting a job. If authority has changed or its coverage check fails, cleanup leaves the job in place instead of writing to a frozen or stale owner; an authorized later invocation can reclaim an expired lease. A real-Go workerd test holds both a successful verifier result and a verifier transport error until after a source freeze, and verifies that the reservation remains byte-for-byte unchanged. The same check covers a changed recovery era. Trigger-definition and missing-table failures also leave cleanup closed until the test restores authority. `node scripts/test-password-split.mjs` and `MAPI_TEST_PREBUILT=1 node scripts/test-upstream-split.mjs` passed locally. This fixes one mutation path in the unmounted experiment; it does not solve the production integration or strict expiry limits above.

### Bounded verifier response

The unmounted real-Go experiment now uses `scripts/private-split-verifier.mjs` for the private service response. It accepts only successful JSON responses with the expected typed fields, limits the response body to 1,024 bytes while reading it, checks a present `Content-Length`, and cancels the reader on an oversized, malformed or aborted response. The password, hash, token and response contents are not logged. `node scripts/test-private-split-verifier.mjs` checks malformed types, lengths, UTF-8, unexpected fields, oversized streaming bodies and aborting a pending body; `MAPI_TEST_PREBUILT=1 node scripts/test-upstream-split.mjs` passed with the real local Go verifier. This bounds the client-side reply, not the verifier's CPU, isolate memory or already-running hash work. The client remains local-only and unmounted.

### Guarded experimental entry

The normal `verifySplit` entry now rejects missing or non-function owner authority, independent registry resolution or admission callbacks before it resolves a route, touches SQLite, or calls the verifier. The old callback-optional behavior is available only through the explicitly named `verifySplitUnsafeForTest` adapter used by the isolated state-machine and latency tests; neither entry is mounted in the application. The real-Go workerd experiment continues to use the guarded entry. `node scripts/test-password-split.mjs` verifies each missing or malformed check causes no side effect, and the state-machine and real-Go `MAPI_TEST_PREBUILT=1 node scripts/test-upstream-split.mjs` regressions passed. The existing single-round local latency probe also passed using the explicit unsafe test adapter; its timings are diagnostic and are not hosted runtime evidence.

This guard prevents accidental omission of the three hooks; it does not make arbitrary callbacks trustworthy. Any production design must construct them inside the owner, bind the route and credential inputs to server state, and meet the policy, retry, admission, recovery and frozen-clock constraints above. The split path remains unmounted.

The local client bounds the password to 1,024 UTF-8 bytes, stored hash to 512 UTF-8 bytes and fully encoded request to 4,096 bytes before calling the verifier, matching the experimental service's transport limits. It rejects oversized data without dispatch, including multibyte and JSON-escape expansion at the exact request boundary. Its bounded response parser rejects duplicate object names, including JSON-escaped aliases, and non-scalar fields before accepting a proof. `node scripts/test-private-split-verifier.mjs` covers boundary and malformed cases, and `MAPI_TEST_PREBUILT=1 node scripts/test-upstream-split.mjs` passed with the real Go verifier. These are experimental transport limits: callers supplying a longer input receive an unavailable result, and exact native error and admission parity remains unproven. Independent review and production credential-policy integration remain necessary.

A focused malformed-binding regression also checks that a synchronous `reader.cancel()` exception cannot replace a valid response or leak its details. The client races a pending body read against its abort signal, so it still returns the generic unavailable error if a defective reader's cancellation throws and leaves `read()` unresolved. The local client and real-Go split tests pass; this does not prove that abort stops a verifier already performing Argon2 work.
