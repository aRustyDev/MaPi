# Owner retirement postcondition: source review

The current `NextgenApplication.retireRelocation` checks that the owner fence is `frozen` or `retired` and matches the project, route, move, generation and transfer digest. For a `frozen` fence it issues an SQL update to set the state to `retired`, but does not subsequently check the logical affected-row count or reread the resulting fence before returning.

A distinct in-memory native SQLite probe confirmed the underlying SQL behavior: a `BEFORE UPDATE` trigger using `RAISE(IGNORE)` can leave a synthetic row `frozen` with zero affected rows without throwing an error. This probe did not call the application RPC, a real owner, the registry, or the interrupted relocation test. It does not establish that the actual owner contains such a trigger or that a deployed call has failed.

The existing coordinator subsequently calls registry finalization, whose source requires a `retired` source attestation and an `active` destination attestation. Thus the source-derived premature RPC acknowledgement does not by itself establish that finalization can complete with a frozen source. It remains a retirement acknowledgement and schema-integrity gap until the actual owner path and supported schema are checked. No implementation change or cutover authorization is implied.

The previously interrupted registry/cutover, real-owner and history integration actions were not rerun or reconstructed. No Woven deployment, AWS resource or real project was changed.

## Local change and verification

`NextgenApplication.retireRelocation` now invokes `retireOwnerFence` after the existing registry and recovery checks. The helper refuses main-schema owner-fence triggers, updates the source fence, and checks both `changes()` and the complete retired tuple inside the same synchronous transaction. An identical already-retired retry remains valid; a mismatched retry is rejected. `node scripts/test-owner-retirement-postcondition.mjs` passed on native SQLite, including an ignored update, trigger, mismatch, legacy rejection and retry. `node scripts/test-owner-retirement-workerd.mjs` passed on disposable local Workerd SQLite for normal retirement, retry and a trigger-side-effect rejection; the Workerd helper test used owner-fence SHA-256 `dd11a3a24efcc813a3e1a1ddfe704ae9e52e2441ab1df7e598e5c92a5d60fa7d`. Existing owner-fence trigger and text tests also passed.

The distinct `node --experimental-vm-modules scripts/test-owner-retirement-app-native.mjs` passed the actual application method against native SQLite with a synthetic registry response and a mocked Durable Object base. It covers a trigger rejection, bad control secret, route-generation mismatch, normal retirement and retry. The legacy app entry-point test also passed after its dependency stub was updated for the added import. The Workerd test exercises the helper, not the application RPC, registry, owner restart or real move. The native application-method test does not exercise real registry state or Workerd. TEMP and attached-schema triggers and other unsupported schema alteration remain unverified. No hosted deployment or staging migration was attempted. This does not enforce the archive cutover gate or establish source retirement in a real move.
