# Experimental FAPI DPoP nonce HTTP boundary

`FAPIPARHTTP` and `FAPITokenHTTP` are private adapters. Neither is mounted by the application, issuer, or staging configuration. This is not a FAPI certification or an assertion that the whole FAPI profile is complete.

The PAR and token operations authenticate the registered private-key-JWT client inside the transaction before resolving a nonce in the server-derived project, client, and endpoint-purpose scope. A signed DPoP proof with a missing, malformed, expired, or out-of-scope nonce rolls that transaction back. The HTTP adapter then issues a fresh nonce in a separate transaction that includes the nonce audit record. It returns `400`, `DPoP-Nonce`, and `{"error":"use_dpop_nonce"}` only when issuance commits. The client must retry with a new DPoP proof and may reuse the client assertion because the failed transaction rolled its replay record back. Missing proofs, bad signatures, proof replay, and invalid clients have generic errors and disclose no nonce. A resource-server caller can use the same internal challenge writer only after authenticating its access token and deriving the trusted scope; it returns `401` and the DPoP `WWW-Authenticate` challenge. Exposing headers does not authorize a cross-origin request.

These helpers depend on correctly enforced transaction rollback and on project identity and the issuer endpoint being supplied by trusted routing. Before any public mount, require HTTPS at the Worker edge; disallow host/forwarded-host spoofing; provide exact endpoint routing, project isolation, CORS policy, bounded request rates and audit retention; integrate a production signing-key lifecycle, session checks, token and resource handling; and run the advertised FAPI and OIDC conformance suites. Limit nonce issuance and cleanup to prevent state growth and load amplification. Do not log form bodies, assertions, DPoP proofs, nonce values, or tokens. The token adapter checks its response has a DPoP token type before committing, but it does not itself prove the access token signature, claims, or `cnf.jkt`; the mint callback and independently verified resource-server path must enforce those properties. The present adapters accept a deliberately narrow grant/form profile and should not be advertised as general OAuth endpoints.

The native full-client fixture exercises the HTTP challenge/retry, nonce expiration, replay, authentication failure, rollback on failed nonce audit, resource challenge, and token exchange. Run `node scripts/test-native-fapi.mjs`; run `node scripts/test-client-assertions.mjs` for the local workerd probe. Workerd tests are not hosted Cloudflare tests; do not deploy this boundary on their evidence alone.

## Local real-session application harness

`node scripts/test-fapi-app.mjs` builds a test-only reactor in a temporary source checkout and runs one SQLite Durable Object in local workerd. It provisions an upstream project and user, completes the pinned password flow and handoff exchange, and passes the resulting real session credential into an unmounted private FAPI probe. The probe authenticates a registered private-key-JWT client, handles PAR and token nonce challenges, consumes PAR into a browser-bound login, validates the authoritative session, and signs a DPoP-bound access token and an ES256 ID token. It checks the signed ID-token issuer, audience, nonce, user, and session; wrong DPoP keys; PAR, login, code, and resource proof replay; rollback of login and token audit writes; and rejection after the upstream session is deleted. The caller preserves the login cookie binding inside the DO test rather than implementing a public browser endpoint. Keys, passwords, and credentials are synthetic.

A local run produced 56,092,385 bytes of Wasm and 108,527,616 bytes of Wasm linear memory, with 1,202 ms for its instrumented synthetic journey. These are one local run, not total isolate memory, a Worker upload measurement, hosted CPU/latency, load capacity, or conformance evidence. The path remains unmounted and its transaction callbacks must execute against the same authoritative storage owner. Public ingress, browser CSRF/cookie integration, independent RP conformance, startup and warm-load budgets, multi-project isolation, hosted validation, and lifecycle controls remain required.

## PAR authorization-code key binding

The private composition accepts a canonical `dpop_jkt` in PAR without a PAR DPoP proof, or a PAR DPoP proof without `dpop_jkt`. If both are present, their thumbprints must match. Present-but-empty thumbprints and DPoP headers are rejected. The committed key is carried through the one-time PAR handle and browser-bound login into the authorization code; token exchange still requires a fresh, verified proof for that key. A code mismatch does not consume the code or retain the client assertion/proof replay records. The result is a DPoP-bound token, not a bearer token.

`node scripts/test-fapi-jkt-only.mjs` runs the proofless-PAR path with a real upstream password-created session in local workerd; `node scripts/test-fapi-app.mjs` runs the proof-header-only path. Both exercise mismatched keys, missing token proofs, replay, and audit rollback. `node scripts/test-native-fapi.mjs` additionally checks a client-authorized resource scope through the proofless chain. These are unmounted private tests, not a FAPI conformance result.
