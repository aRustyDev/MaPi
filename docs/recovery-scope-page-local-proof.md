# Local recovery scope page validation

The registry's `captureRecoveryScopes` now validates an owner page before hashing or persisting it. The page and each row must use the pinned producer's canonical field order, the cursor must equal the final row (or the prior cursor for an empty terminal page), and rows must advance strictly beyond the prior cursor in SQLite BINARY order. Scope text is validated for project ownership, canonical Go JSON and well-formed Unicode; stamps must be nonnegative signed 64-bit values at or below the anchored clock. The registry measures the complete JSON-encoded page, including escaping and repeated cursor, and rejects pages above 124 KiB. An initial UTF-16 length check rejects obviously oversized keys before encoding them. The owner RPC has already materialized its response, so this does not bound inbound RPC memory or SQLite scan cost.

`node scripts/test-recovery-scope-page.mjs` passed against disposable local workerd on November 23, 2026. It invokes the real registry capture method with a synthetic recovery-status test double and a real Durable Object RPC for page transfer. The owner-producer result preserved the expected page/row field order through that local RPC. An ordering vector checks that U+E000 precedes U+10000 in UTF-8 byte order, despite their opposite JavaScript UTF-16 order. Reversed rows, duplicates, non-advancing cursors, an invalid terminal cursor, foreign scopes, out-of-range stamps, unexpected properties, reordered fields, an unpaired surrogate and oversized pages were rejected without changing an existing checkpoint or its anchor rows. A backslash-heavy page measured 126,974 encoded bytes and passed; the next candidate measured 126,982 bytes and failed the 126,976-byte limit. An empty terminal page retaining the prior cursor completed successfully.

The existing method creates an empty checkpoint before requesting its first page; the test confirms that an invalid first page can leave that zero-progress checkpoint, while inserting no anchors. Canonical field-order checks deliberately fail closed for older or future owners that serialize equivalent fields in a different order; deployed writer compatibility must be established before use. The test does not independently establish complete source pages, scope truth, writer drain, PITR, hosted behavior, or recovery reopening. Actual coordinated restore remains disabled.

An attempted repeat of the focused test after adding separate oversized-nonfinal-scope and 65-row assertions was aborted before dispatch without a stated reason and was not retried. The implementer reports removing those assertions and leaving the production validator and capture integration unchanged since the pass. The run used an unfrozen working checkout, and byte-identical restoration of the test source was not independently verified; neither added case is claimed as tested.

The registry now validates checkpoint identity, nonnegative safe integer count, exact `done` value, cursor and digest before the completed-checkpoint fast path and before serving scope status or snapshots. It compares the count as well as cursor, digest and completion state after the owner RPC, checks for count overflow before inserting anchors, and rejects a changed recovery owner, object ID, origin, generation or epoch. A repeat of `node scripts/test-recovery-scope-page.mjs` passed in local Workerd for malformed and foreign checkpoints, an in-flight count change, an in-flight owner change, overflow, and a successful retry after restoring each test fixture. The test uses a synthetic status fixture and does not prove checkpoint authenticity, actual anchor cardinality, complete owner pages, independent nonrollback authority or safe recovery reopening. Those gates remain open.
