# Private Console management-read proof

This local-only Worker combines the pinned Console assets, the upstream official password login and session, and the previously tested upstream user-read and user-query management handlers. Its management ingress uses the existing `worker/management-proxy.js`; a test-only Durable Object wrapper also checks the project and origin in the same synchronous owner turn that calls the upstream handler. It is not mounted by the application or deployed. Fixture endpoints are localhost-only and require the synthetic operator token: never deploy them.

After building the pinned Console assets and empty baseline as described in [console-static-investigation.md](console-static-investigation.md) and [console-runtime-proof.md](console-runtime-proof.md), run:

```sh
MAPI_CONSOLE_DIST=/private/tmp/mapi-console-proof/apps/api/internal/staticui/console/dist node scripts/build-console-static-proof.mjs
GOPROXY=off GOMODCACHE=/private/tmp/zitadel-nextgen-poc/go-mod GOCACHE=/private/tmp/zitadel-nextgen-poc/go-cache node scripts/build-console-management-proof.mjs
node scripts/test-console-management-proof.mjs
node scripts/test-native-console-management-session.mjs
```

The Playwright journey signs in through the actual Console component and obtains an upstream session. The session initially cannot query users. A private test fixture directly inserts a synthetic project-admin assignment; the same session then successfully reads its own user and queries the owning project's users, including from browser JavaScript. Revoking that assignment in authoritative SQLite makes the next query fail while the session remains valid. The test creates another real project object and user, verifies its own session's user ID and admin query, and checks each project's user is absent from the other's list. Cookies crossing projects, absent or invalid credentials, an invalid Bearer accompanying a session, foreign selectors, wrong methods, cross-origin and `Sec-Fetch-Site: cross-site` requests are rejected. Spoofed forwarding headers do not affect the tested query. The management response is `no-store` and does not contain the synthetic operator token, password or session credential. A separate logout check verifies CSRF, cookie clearing and rejection of the revoked session.

The pinned `POST /users/query` is a read operation explicitly exempt from the upstream CSRF-token check: the test verifies that the otherwise authorized query still succeeds with an invalid CSRF token, while cross-origin restrictions remain in force. This is not evidence that a management mutation enforces CSRF. The admin grant is inserted and revoked directly as synthetic fixture data, so the test does not prove grant creation, grant auditing, delegated administration or a real Console admin provisioning workflow. The browser uses `fetch` in the Console page rather than proving that a Console management screen renders or navigates correctly. A separate native SQLite session test applies the same synthetic grant and asserts the same unprivileged, granted and revoked statuses (404, 200 and 404) and a still-valid session after revocation; it also verifies invalid Bearer precedence and the query's CSRF exemption. This is a narrow native comparison, not full response-body or delegated-authorization parity.

The existing application entry point deliberately treats `localhost`, `127.0.0.1`, and `[::1]` on the configured loopback port as the configured local origin. Calling its operator user-creation endpoint with the alternate hostname therefore creates a user in the configured project. This test avoids that shortcut: its private fixture resolves the exact registry origin and seeds the second user directly in that project's object, then authenticates that user and confirms the owner project's session response and user query. The checked Woven staging configuration uses a non-loopback HTTPS hostname, so the loopback-only condition in `worker/app.js` is not selected for that configured hostname. This is a source/configuration observation, not a hosted routing test or proof of deployed multi-origin isolation.

The registry lookup, identity check and owner call remain separate operations, and the project route has no production relocation generation fence. Full management API coverage, real administration and membership state, grant-revocation races, request auditing, signed-in Console management screens, public ingress, hosted memory/CPU and workload tests remain open. The default official login also still exposes the known-versus-unknown identifier distinction documented in [console-flow-proof.md](console-flow-proof.md). The browser flow still exposes its one-time handoff to the component and uses the existing internal exchange credential; neither concern is addressed by this test.
