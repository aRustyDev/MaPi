# Hosted synthetic handoff repeat

On November 19, 2026, a fresh synthetic owner `mapi-p1-rehearsal-4c8336c46012303b9fbd4367b3e46b68-owner`, secondary router and private control were created with three namespace IDs absent from the pre-deployment inventory. The owner upload was 54,966.26 KiB uncompressed and its later enabled version `2a0cbb6b-701d-4cc4-91de-46850493110b` validated startup in 107 ms. The private control version `6be4e542-c4fa-497a-b7d4-8e6c7708b958` used a fixed-project batch endpoint limited to four serial coordinator advances per request. An immutable bundle was used; Cloudflare's downloaded disabled owner JavaScript and all 56,019,930 Wasm bytes matched it byte-for-byte, as did the bounded control JavaScript. The Wasm SHA-256 was `979cdf5386076ef0bda76ef7e21e8a869a55726cbb8b3f9f5eb5d58e6e0fbc65`. Enabled-version provenance verified the same three namespace IDs, approved 100%-traffic owner/router/control versions, full invocation logging, fixed synthetic project and move IDs, and no public route, domain, workers.dev or preview for control.

The initial new router and control uploads returned Cloudflare error 10007 while Wrangler configured targets. Read-only inspection found both scripts and versions existed, the private control endpoint was disabled, and the router's workers.dev endpoint was disabled. The router was explicitly redeployed and then verified. Another enabled-provenance query failed closed on inconsistent deployment pagination and passed on a later read-only recheck. These setup failures are recorded and are not counted as successful move steps. Cloudflare deployment metadata for an intervening rebaseline was delayed; the verifier proceeded only after the active versions appeared and their actual bytes were checked.

The first application-source move completed in one driver run with 119 coordinator advances and 119 concurrent second-project management reads. Its pending handoff was already expired by the time the move began: it was created before the enabled deployment and provenance checks. The exchange returned 400/400; the endpoint categorized it as expired. The first move's journal and stale-source rejection passed. This is not evidence that a valid handoff survived that move.

To exercise a still-valid handoff without changing the product's 60-second TTL, the same originally legacy synthetic project was moved a second time, from generation 2 to generation 3. The enabled versions and private bindings were reverified after installing the bounded batch control. A fresh handoff was created at **22:45:55.432 UTC**, immediately followed by read-only provenance. The move ran from **22:46:00.138 to 22:46:44.277 UTC**; exchange completed at **22:46:45.686 UTC** with statuses **200 and 400**, proving one successful exchange and one rejected replay within the TTL. The driver made 30 control calls containing 119 serialized coordinator advances and 30 concurrent Go-backed management reads; it reported no call or read failures. Management responses were fully consumed with a 1 MiB bound rather than canceled. Both outcomes of every concurrent pair were recorded; this comparison does not establish the cause of earlier connection resets.

The private journal returned **59 reconciled digest pages**, including one original user and **46 historical audit events**. A subsequent verification preserved the project ID, returned 200 for the prior active session and 303 for the revoked session, accepted both project users' credentials, and rejected cross-project credentials. A post-move synthetic user creation and login succeeded in the moved project and failed in the other project. Stale-source rejection was verified for the first application-source move; this second generation-2 source was not separately probed. Hosted coordinator/owner restart injection after activation was not performed.

A read-only Workers Observability query for **22:45:50–22:46:50 UTC** returned owner outcomes of 35 fetch and 3,948 RPC `ok` records, router 30 fetch `ok` records and control 30 fetch `ok` records. Each nonempty outcome aggregate had `sampleInterval: 1`; no other outcome groups or `mapi.overload` markers appeared in the returned data. CPU-time aggregates were available for only a subset: 866 owner RPC records had 5 ms p95 and 817 ms maximum; router had one and control had 16 CPU-valued records. These are invocation measurements, not a complete per-invocation CPU accounting. A `durableObjectsPeriodicGroups` query for the owner namespace and same window returned no samples at the time of the check, so isolate-memory coverage and periodic platform-limit counts remain unverified. The full runtime benchmark and hosted restart scenarios remain open.
