# Audit shadow lifecycle: native SQLite experiment

The detached-frame reader now checks `total_changes()` around its synchronous
read callback and rejects writes inside the same transaction. Before the fix,
`node experiments/audit-snapshot/shadow-reader-readonly-native-test.mjs`
failed because a callback could insert into a business table and still return
a frame. Afterward it passed for an insert and for insert-then-delete, checking
rollback, the still-active lease, and a subsequent ordinary read. The lifecycle,
authorization-readonly and frame-brand native tests also passed. A disposable
local Workerd regression passed the insert-then-delete reader case; see
`audit-shadow-guards-workerd-local-proof.md`. The callback remains trusted: the
counter does not detect DDL, non-SQL side effects, or async continuations. This
is unmounted and does not establish actual handler authorization, snapshot
completeness, bounded callback memory, or hosted behavior.

`experiments/audit-snapshot/shadow-lifecycle.mjs` is an unmounted local experiment around the pinned-schema shadow installer. It is not an application route, migration, project authority, cleanup service or deployable snapshot. The existing installer was split into an in-transaction helper and its original transactional wrapper so creation of the shadow structures and lifecycle row can commit or roll back together.

The experiment checks the owner tuple and recovery era and calls a **trusted synchronous, read-only** authorization callback inside every transaction. It records a manifest of source and shadow schema objects and compares it before access or cleanup. Each logical reader use registers a persistent `(reader_id, use_id)` lease. An active use blocks closure; a released pair cannot be reacquired, and corrupted or future lease states also block closure. Repeating the same active pair is an idempotent lost-acknowledgement retry. A trusted allocator must assign a distinct, unguessable use ID to every logical consumer; this module cannot distinguish two consumers given the same pair and cannot enforce that requirement by itself. Closing atomically checks for no active leases, disables acquisition and removes the shadow view and event triggers. Normal event writes continue through copy-on-write triggers while active and through the original event table after closure. Cleanup deletes at most a caller-selected diagnostic count of rows per transaction, then retains a scoped terminal tombstone so a lost completion acknowledgement can be reconciled. A separate status read can reconcile an uncertain begin or close. A new snapshot cannot replace a terminal tombstone: a separately authorized archive/reset protocol is not implemented.

The distinct local command `node experiments/audit-snapshot/shadow-lifecycle-native-test.mjs` passed using a temporary on-disk native SQLite database and the generated baseline event DDL and 12 indexes. It covered atomic install rollback, multiple active readers and two overlapping uses of the same reader ID, idempotent duplicate acquisition and release, denial of closed or released uses, persistent leases across database close/reopen, route and era mismatches, a missing trigger, cleanup denial while a reader is active, an invalid persisted reader state, cleanup rollback after authorization failure, bounded-row cleanup, repeated close and terminal cleanup after lost acknowledgements, and route freeze. In the overlap case the test releases one use while the second is the only remaining active lease, verifies the second still reads and close remains denied, then releases it. The same command initially exited 1 before assertions because the native storage adapter omitted `.one()`; after correcting the adapter, it passed. `node experiments/audit-snapshot/shadow-sql-native-test.mjs` also passed after the installer refactor.

The same native lifecycle command passed after the read contract was narrowed to one encoded `Uint8Array` frame per call, at most 128 KiB. The frame is copied inside the transaction before the final authority check; an empty frame remains valid, and the test confirms source-buffer mutation and lease release do not alter the returned copy. It rejects a synthetic non-frame object, a 256 KiB frame and an asynchronous callback. The cap is on each encoded transport frame, not on an event or response page. This test did not exercise a live SQLite cursor or the interrupted bridge-cursor work.

The distinct `node experiments/audit-snapshot/shadow-frame-brand-native-test.mjs` passed after replacing the prototype-dependent shared-buffer check with the intrinsic `ArrayBuffer` byte-length getter. In native Node SQLite, it rejects a `Uint8Array` backed by a `SharedArrayBuffer` whose prototype was changed to `ArrayBuffer.prototype`, and copies an ordinary offset view without retaining the original buffer. This checks the backing-store brand for those synthetic cases; it does not test other realms, Workerd availability, concurrent mutation, actual reader authorization, or the callback's internal memory use. It does not repeat the interrupted cursor work.

The main-schema manifest did not cover TEMP objects. A new native test showed that an arbitrary TEMP trigger on the main reader table ran during reader acquisition without detection; its initial run failed at the expected-denial assertion. The lifecycle guard now rejects TEMP objects in the source/snapshot namespaces and TEMP triggers on those tables before and after its trusted authorization callback. `node experiments/audit-snapshot/shadow-temp-schema-native-test.mjs` passed for an events trigger before begin, a reader trigger during acquisition, case-varied TEMP reader and event tables, a TEMP snapshot view, and normal acquisition after removal. The original lifecycle and frame-brand tests also passed after the change. These checks cover the unmounted experiment, not its separate owner-fence or recovery-authority tables. Local Workerd could query an empty TEMP catalog, but rejected the attempted TEMP fixtures before the guard ran; see `audit-shadow-guards-workerd-local-proof.md`.

The synchronous authorization callback previously could write a row and return true without rejection; the dedicated native test reproduced this before the change. The guard now compares `CAST(total_changes() AS TEXT)` before and after that callback within its transaction. `node experiments/audit-snapshot/shadow-authorize-readonly-native-test.mjs` passed for insert-then-delete during begin and reader acquisition, checking rollback and a subsequent successful read-only callback. The existing lifecycle, TEMP-schema and main-schema case regressions also passed. A separate disposable Workerd check exercised normal lifecycle operation and rollback after the same kind of callback write; see `audit-shadow-guards-workerd-local-proof.md`. This check does not detect DDL, non-SQL side effects or asynchronous work scheduled for later; the authorization callback remains trusted and must be synchronous. It does not establish actual Go authorization, reader isolation, bounded snapshot memory, a production owner, or hosted behavior.

SQLite resolves identifiers case-insensitively but stores the spelling used to name a trigger's target in `sqlite_schema.tbl_name`. A distinct native regression initially showed a trigger targeting `EVENTS` could evade the installer’s source-trigger check. The installer now checks source indexes and triggers case-insensitively; the lifecycle manifest uses case-insensitive source, shadow and reader table names, and existence checks recognize case-varied orphan names. `node experiments/audit-snapshot/shadow-main-case-native-test.mjs` passed for the pre-install uppercase source trigger, an extra trigger on the uppercase reader-table spelling, a case-varied orphan and normal subsequent acquisition. The lifecycle, TEMP guard and shadow SQL native suites also passed. This concerns the unmounted audit shadow prototype, not the separate, accepted application owner-fence metadata limitation. It does not prove actual authorization, transfer, complete snapshot behavior, Workerd or hosted behavior.

## Open boundaries

- No real application reader acquires these leases. Cleanup is safe only if every logical consumer receives a unique use ID, acquires before accessing any shadow data and releases only after it no longer needs the data. Duplicate holders of an identical pair remain indistinguishable; a trusted durable allocator or stronger ownership protocol is needed. The copied-frame contract rejects returning a live object directly, but cannot prevent a trusted callback from retaining storage handles elsewhere; it does not bound the callback's own query or memory. A crashed or lost reader deliberately leaves cleanup blocked; authenticated repair, lease finalization and recovery-era transitions are not implemented. The trusted authorization and read callbacks must not mutate storage or schedule later mutation.
- The manifest is stored in the same SQLite database as the schema. A writer able to modify both can forge it; independent authority, source-version identity, protected shadow data, complete history and exclusion of direct SQL bypasses remain unproven. The owner-fence helper still materializes stored route fields.
- A row count is not a byte, CPU, time or SQLite-internal-memory bound. Schema comparison, table drops and individual rows can be expensive. There is no quota reservation, retention policy, encrypted storage, distributed reader admission or tested failure behavior under storage exhaustion. The 64-row maximum in this diagnostic is not an accepted production limit.
- Native SQLite close/reopen simulates a restart but does not prove process crash, object eviction, Workerd concurrency, Cloudflare transaction behavior or hosted recovery. Real event query authorization, pagination, ordering, error parity, full-response framing and integrity are not integrated. The prior interrupted exact-size, nonfinite, malformed-TEXT, cursor, SQL-limit, normalization, combined archive and hosted actions were not rerun.
