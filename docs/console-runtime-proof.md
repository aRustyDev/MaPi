# Console runtime bootstrap: local-only proof

This isolated proof creates two real, independently owned `NextgenApplication` SQLite Durable Objects and uses the existing `ProjectRegistry`. It does not change application ingress or deploy any Worker. The test-only reactor exports an adaptation of pinned `cmd/server/console_runtime.go`: retrieve the authoritative project, reuse an active preview token if present, or use the upstream token service to mint and audit a new preview token; then use the upstream project token key to encrypt it. The response contains only `mode`, `console_project_id`, and `publishable_key` with `Cache-Control: no-store`. As in native Nextgen, JWE ciphertext can change between reads even when the same token record is reused.

The local proof intentionally adds guards that are **stricter than pinned native runtime semantics**: the registry route must be active; the origin, project ID, recovery epoch and maintenance state must match in the owner object's synchronous turn; the project and its primary deployment must resolve; and the resulting token must introspect as this project's `project_preview` with exactly `project.read`. An unprovisioned project answers 503 instead of native's empty standalone document. A request containing an `Origin` header must match the URL origin; same-origin navigation without an Origin header is permitted. Forwarded-host/proto headers do not select the route. These differences are test design choices, not a parity claim.

From MaPi, after generating the empty baseline described in the main setup (`node scripts/baseline.mjs`), run:

```sh
GOPROXY=off GOMODCACHE=/private/tmp/zitadel-nextgen-poc/go-mod GOCACHE=/private/tmp/zitadel-nextgen-poc/go-cache node scripts/build-console-runtime-proof.mjs
node scripts/test-console-runtime-proof.mjs
```

The build uses the pinned archive, Go 1.26.9, the local management read adapter and a separate `mapi_console_runtime_probe` export. It produces ignored files under `worker/generated/`; measured Wasm size is 53,246,685 bytes, excluding JavaScript and static assets. The test provisions both projects from empty databases, checks eight concurrent first reads, origin and owner fences, Host/forwarding behavior, GET/HEAD/method behavior, and persists both across a local workerd restart. It uses synthetic keys and does not print credentials.

The native `@zitadel/testing` server's runtime resolves its reserved platform project in this setup. Its preview credential and the Worker's respective project preview credential both receive 403 from the actual upstream user-query management handler, while a real project secret succeeds with 200. A preview key from one Worker object receives 401 at the other object. The Worker key is additionally introspected by the upstream Go token service before publication, proving its type, owning project, and restricted scope. This establishes the tested denial and separation; it does not establish successful browser flow calls with this credential, preview-key revocation/rotation, or full origin enforcement in those calls.

The test-only ingress includes operator-protected diagnostic endpoints for producing a project secret and forwarding a management query. They exist solely to make the security assertions and must never be deployed. The actual Console static proof remains separate, uses synthetic runtime, and does not integrate this bootstrap. Real `/api/v1` flow, exchange, sessions, CSRF, Console management and delegated authorization are not complete or exposed. In particular the experimental flow read path and upstream Console suites still need resolution before an authenticated browser journey is possible.

The registry read and owner call are separate operations, not a cross-object transaction. The owner checks the supplied identity and origin at execution time, but a production relocation, route-generation change or revocation must additionally fence stale routes, including the gap between the registry read and owner call. This harness does not prove relocation or registry cache invalidation. Durable Object isolation, local restart, or a correctly shaped runtime document do not by themselves prove production authentication, hosted limits, or authorization. The runtime proof's extra checks and issuance behavior require review and security testing before any public integration.
