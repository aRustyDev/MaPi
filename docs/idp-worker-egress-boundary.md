# Private Workers egress boundary investigation

Tenant-supplied IdP URLs are **not enabled** by this experiment. The pinned Nextgen [egress policy](https://github.com/zitadel/nextgen/blob/b0b74cd4a198428ea9b82910c217259ffc62b65c/docs/adrs/061-egress-policy-user-injectable-urls.md) requires a decision on the actual address at connection time, direct connections, TLS validation for the requested host, and a fresh policy check at every redirect. It also bounds response bytes and deadlines and prevents cross-origin credential forwarding. Hostname validation or DNS lookup before a later `fetch()` cannot establish that the fetched connection used the approved address.

## Lower-level socket diagnostic

The following is an opt-in **local workerd** diagnostic, not an application transport or a hosted test. It opens TLS sockets to one fixed public host, `www.google.com`, and sends no HTTP, project data, or credentials. Without the flag it makes no external request.

```sh
MAPI_SOCKET_PUBLIC_PROBE=1 node scripts/test-socket-peer-probe.mjs
```

The script prints JSON and deliberately exits nonzero: it does not demonstrate the required pre-connect address enforcement or separate host validation on a numeric-IP dial. On November 19, 2026, Wrangler 4.165.0 local workerd opened a TLS socket to the hostname but reported `SocketInfo.remoteAddress` as `www.google.com:443`, rather than a numeric peer. The same hostname's resolved public IPv4 used as the socket address failed at the local proxy with `proxy request failed, cannot connect to the specified address`. No HTTP request was sent. Network outages, DNS changes and different runtime versions can change the observations. The test does not prove platform-wide behavior or private-network reachability.

Cloudflare documents that [`SocketInfo.remoteAddress` may be unavailable](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/#socketinfo), recommends `fetch` for HTTP on ports 80 and 443, and [does not support ordinary `fetch` to IP-literal URLs](https://developers.cloudflare.com/workers/platform/known-issues/#fetch-to-ip-addresses). The separate [Node TLS probe](idp-tls-pinning-probe.md) observed an ineffective `servername` override and a failed IP connection locally. Neither hostname-valued peer metadata, `socket.authorized`, nor a prior DNS answer is proof of the actual target. Even a future numeric peer result would not by itself show that an unsafe address was blocked **before** the socket connected or that TLS validates the original hostname.

## Candidate platform boundaries

1. **Gateway-backed Worker egress:** [Workers VPC](https://developers.cloudflare.com/workers-vpc/configuration/vpc-networks/#egress-to-the-public-internet) can route explicit `env.EGRESS.fetch()` calls through Cloudflare Gateway, which offers destination-IP network policies. This is a candidate, not an equivalent proven implementation. The account needs Zero Trust/Gateway with the proxy enabled; global `fetch()` bypasses the binding. The `cf1:network` binding also reaches the account's default private Mesh, Tunnel and WAN routes, so an unsafe or bypassed policy can increase access to internal services. Workers VPC is beta. Verify policy ordering, traffic identity and no fallback/bypass, IPv4/IPv6 and NAT64 handling, hostname and TLS integrity, each redirect hop, connection-time destination enforcement, outages, credential/log redaction, and the account's existing routing before considering it.
2. **Private Cloudflare Container workload:** [Containers](https://developers.cloudflare.com/containers/) run Linux workloads behind a Durable Object; running pinned upstream Go's hardened `net.Dialer.Control` inside a narrowly scoped, private container is a possible fallback after a measured Workers limitation. This has not been tested on Cloudflare and is not assumed safe. A real design must verify the container's actual networking path, any proxies or transparent intercepts, TLS trust, DNS rebinding and connection-time denial, and must preserve authoritative state and transactional audits in the owning Durable Object. Cloudflare notes that with [`enableInternet: false`](https://developers.cloudflare.com/containers/configuration/outbound-traffic/#block-outbound-traffic), intercepted DNS returns placeholder addresses and HTTP(S) exits through a Worker handler; that arrangement cannot be assumed to preserve the native Go dial-time check. With internet enabled, restrict all applicable protocols and ports at a verified boundary rather than assuming HTTP intercepts cover arbitrary traffic.

Neither alternative has a staging configuration or implementation here. To close this gate, use an isolated account/project with synthetic providers and adversarial DNS answers; test initial and redirect destinations across loopback, private, link-local, mapped IPv4, IPv6, NAT64, public/private rebinding and credential-bearing cross-origin redirects. Verify the **actual** destination used, TLS certificate/hostname, policy failure behavior, byte and time limits, cancellation, per-request and whole-operation deadlines, redacted logs, and no automatic reuse of a possibly consumed authorization code. Repeat after eviction, on hosted Cloudflare, and under load. Do not enable arbitrary user-controlled provider URLs until those checks and the existing upstream-state transaction/recovery tests pass.
