# Audit shadow table: pinned-schema native diagnostic

`experiments/audit-snapshot/shadow-sql.mjs` and its native test are an unmounted, local experiment. They do not install an application schema migration, serve a route, authorize a real user, or create a production snapshot. No Woven resource is accessed. The installer takes a trusted pinned DDL and index list, requires an externally supplied synchronous authority callback, and runs installation in the supplied synchronous transaction. Its callback is a test double, not authentication or proof that a registry route is current.

The experiment checks the source `events` DDL against the supplied pinned baseline and compares the named explicit indexes, rejects pre-existing source triggers and extra unique indexes, then clones the table DDL and all 12 filtering indexes under private names. A single snapshot's triggers save a whole original row, including its SQLite rowid, into the identically declared shadow table before it can be changed or replaced, and mark post-snapshot rowids with conditional inserts. A private `UNION ALL` view combines saved rows with unchanged live rows. Whole rows remain inside SQLite; this is not a bounded transfer, encrypted storage, source-integrity authority or lifecycle protocol.

`node experiments/audit-snapshot/shadow-sql-native-test.mjs` exited 0 using Node SQLite and the existing generated baseline DDL. The test selects the table DDL and all 12 index DDLs directly from that file, verifies the source SQLite definitions match them exactly, then compares against a separate unchanged native database. The baseline file was not regenerated, and the historical exporter/sequence gap remains open. It checks sampled project, category, creation-time, actor, status and event-type filters and a second project's scope, TEXT/numeric and INTEGER/text comparison affinity, source rowids, ordering, and selected value types and byte lengths. It compares results before and after synthetic new inserts, a no-op conflict, `UPDATE OR FAIL` and `UPDATE OR ABORT`, `INSERT OR REPLACE`, `UPDATE OR REPLACE`, delete and transaction rollback. One synthetic BLOB is 131,073 bytes, but the query checks its length/type rather than copying it through JavaScript. Failed authorization at the end of installation rolls back all created objects.

The SHA-256 values measured after the run were: baseline `c91d739a66d18c77f837cc334d8e7242aaaaabe6499387703e5ddf067d5ffb98`, installer `8736165c2c6e1aee4507d00ec334363ab1d0abae20ccb5b6ed0761f55b624183`, and native test `f47a879b7a221fc74f5c1e102dee7b6a38d67977f7e0dd733886e2660f9e555a`. The files were not frozen or rehashed before execution; these identify the files inspected after the test rather than proving immutable run provenance.

This does not establish full SQLite or Go event-handler parity. The input schema is trusted rather than independently authenticated; the prototype has no deployed fence, immutable trigger/schema protection, owner-generation or recovery-era integration, authenticated selector, concurrency or multi-snapshot protocol, retention policy, cleanup, quota, error or crash-recovery protocol. It copies whole rows into SQLite and does not establish platform row-limit equivalence, SQLite internal memory, storage, CPU, or Worker resource bounds. It does not demonstrate all original scan/lookahead errors, filters, page and cursor behavior, stable tie behavior across plans, serialization, authorization or Workerd. The prior interrupted exact-size, nonfinite, malformed-TEXT, cursor, SQL-limit, normalization and hosted actions were not rerun.
