# Reactor initialization attempt markers: local evidence

When `MAPI_RUNTIME_DIAGNOSTICS=1`, the owner now emits `mapi.reactor.start` and `mapi.reactor.failure` markers and adds the same per-instance attempt number to the existing `mapi.reactor.ready` marker. Start is emitted before reactor instantiation; failure is emitted when initialization throws. The existing ready marker retains its `event`, `bootId`, `objectId`, `initialization`, and `wasmHighWaterBytes` fields. Markers include no request input or exception details. Metadata acquisition and lifecycle logging are best-effort and must not change initialization if they fail. Attempts increment on each initialization attempt in an owner instance; success counts remain separate.

`node scripts/test-runtime-diagnostics.mjs` passed for disabled logging, a failed first attempt followed by a successful second attempt, sanitized fields, and throwing log sinks. The existing `node --experimental-vm-modules scripts/test-legacy-body-boundary.mjs` and `node --experimental-vm-modules scripts/test-owner-retirement-app-native.mjs` passed after their VM import mocks were updated. `node --check worker/app.js` also passed. The logs in the emitter test are invoked directly; these tests did not exercise a real Go reactor initialization, cloud log delivery, error classification or timing. Logging sampling and platform log loss can still make a lifecycle trace incomplete; absence of a failure marker does not prove that initialization succeeded.
