# Local relocation move-ID admission

Before creating a new relocation intent, the registry now requires a nonempty, well-formed Unicode move ID of at most 128 UTF-8 bytes. The length check first rejects more than 128 UTF-16 code units, then validates surrogate pairs and measures the bounded value with `TextEncoder`. A rejected ID does not create an intent or ask the source owner to freeze. This restriction is applied only when creating a new intent. Existing intents, moving routes and committed moves keep their original ID so a move started by older code can be retried even if that ID exceeds the new limit.

`node scripts/test-registry-move.mjs` passed against disposable local workerd. It exercised a UUID, exactly 128 ASCII bytes, exactly 128 bytes of supplementary Unicode, oversized ASCII and multibyte values, unpaired surrogates, and a reused ID. For rejected new IDs and reuse it compared the registry route, intent, move, ID and object counts and verified the synthetic source owner was not asked to freeze. The test also seeded a 129-byte legacy intent and retried it while moving and after a synthetic committed cutover. Expected rejection and eviction errors appear in the local test logs.

The registry RPC has already received and materialized the supplied string before this admission check; this is not an inbound request-size bound. A valid ID is only an identifier, not authorization or proof of the move's data. This local test uses synthetic owner attestations and does not prove hosted writer drain, recovery, or authorization for a real singleton move.
