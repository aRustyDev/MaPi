# Audit shadow start in a caller-held transaction

The unmounted shadow lifecycle now exposes `beginShadowInTransaction`, which shares the existing guarded implementation with `beginShadow`. The existing wrapper still copies its scope before opening its own synchronous transaction. The new entry is **trusted-only**: its caller must already hold the same synchronous SQLite transaction as any authorization decision, and must roll it back on failure. The helper cannot itself verify that a transaction exists or that the caller's authorization is real.

The disposable local Workerd command `node experiments/audit-snapshot/shadow-begin-in-transaction-workerd-test.mjs` passed. It verifies denial before creating a shadow, rollback of a prior business marker and all shadow schema after an injected outer exception, successful joint commit, and duplicate rejection through the existing wrapper. These are actual local Workerd SQLite transactions with a synthetic authorization callback; they do not exercise the real Go handler, real owner, network authorization, or interrupted handler/transfer tests. `node experiments/audit-snapshot/shadow-lifecycle-native-test.mjs`, `node experiments/audit-snapshot/shadow-authorize-readonly-native-test.mjs`, and `node experiments/audit-snapshot/shadow-sort-checkpoint-native-test.mjs` also passed after the refactor.

The Workerd run used lifecycle SHA-256 `94b821c7a95d971d764f0d7292d982248174f8aad94d9a602499758ed263fd0c` and generated test-worker SHA-256 `1feaf8d9b0796cead85719fc2b6d875a880f5d8afa6efb053485aacb4c685a4c`. No process remains live.

This refactor does not establish a Go-to-host bridge, the real caller-held transaction, pinned authorization or visibility, handler error precedence, complete bounded snapshot or hosted behavior. Invoking the trusted entry without an encompassing transaction can leave partial state and is unsupported. The previously deferred handler and owner integration remain open. No Woven deployment or AWS resource was changed.
