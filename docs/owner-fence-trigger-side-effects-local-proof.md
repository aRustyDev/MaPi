# Owner fence transition trigger guard

The owner's SQLite fence transitions must not acknowledge a valid fence row while an unexpected trigger mutates unrelated business or audit state. A distinct synthetic native SQLite probe showed that an `AFTER INSERT` trigger could modify a business row and still leave `initializeOwnerFence`'s prior row postcondition satisfied. The previous initialization and freeze proofs only exercised triggers that ignored or undid the fence update.

`initializeOwnerFence` and `freezeOwnerFence` now check for triggers attached to `mapi_owner_fence` inside the same synchronous transaction before their transition. Matching `sqlite_schema.tbl_name` uses `COLLATE NOCASE`, because SQLite resolves ASCII identifier case insensitively even when the stored table name retains uppercase spelling. Both helpers retain their existing exact row and logical affected-row postconditions. The guard fails closed for **any** trigger on this table; an actual owner inventory must identify any legitimate triggers before this code is adopted.

`node scripts/test-owner-fence-trigger-guard.mjs` passed on native Node SQLite. It checks synthetic insert/update triggers that modify business and audit rows while leaving the fence otherwise valid, an uppercase stored table name, no changed business/audit or fence state on rejection, and valid initialization/freeze plus identical retries. The first run before the guard and the intermediate run before the case-insensitive fix each exited 1 with the expected missing-rejection assertion. This is a synthetic fixture, not the actual owner or a proof of privileged DDL isolation.

`node scripts/test-owner-fence.mjs` passed on disposable local workerd after scoped approval for a loopback listener. The initial sandboxed attempt exited with `EPERM` before assertions. The standalone fixture now includes side-effect-only insert/update triggers and an uppercase-table case in addition to the earlier ignore/undo, normal operation, stale route and eviction checks. Fault logs are expected. The relevant final file SHA-256 values were `fcadb9fa6f23c66d382b8988c590eab6d6390564343adea5fea9e70fdd02df06` for `worker/owner-fence.js`, `7874206e3e2fa0cf654935cf4857382d11831717b292c0e56e0dfd7407421225` for the distinct native test and `302d0aec4e7904cfeb2289afa4e3a2b434a7203b5b39b8c99448155a39b97054` for the standalone Workerd test Worker.

This guard checks the main `sqlite_schema` only. It does not prove that TEMP or attached-schema triggers are impossible or blocked, validate the complete fence schema, protect against an actor able to alter schema concurrently outside the transaction, or guard direct fence writes elsewhere in the application. No real-owner migration, interrupted registry/history action, hosted deployment or Woven resource was exercised. Complete mutation-path fencing, writer drain, archive authorization and Phase 1 sign-off remain open.
