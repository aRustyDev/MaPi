# Local destination reservation checks

`reserveMoveDestination` now validates the stored reservation table before trusting an existing row or inserting a new one. It requires the canonical six-column definition with its singleton primary-key check and rejects explicit indexes, triggers and rows with a singleton other than 1. The definition comparison normalizes ASCII whitespace runs and ASCII case; it deliberately requires the same punctuation spacing and rejects other equivalent SQL spellings. A legacy or damaged noncanonical control table therefore fails closed and requires separate review, not automatic repair. SQLite compares the requested route and move tuple without returning stored control values to JavaScript.

`node scripts/test-owner-fence.mjs` passed in disposable local workerd. Its fixtures exercised an occupied destination, an existing view, missing constraints, non-ASCII identifier whitespace, noncanonical punctuation spacing, an extra index or trigger, and an extra singleton inserted with test-only constraint suppression. Rejected calls left captured schema, reservation rows and synthetic business/audit rows unchanged; the occupied-destination case also rolled back the newly created reservation table. Canonical ASCII case and whitespace-run variations passed. A matching reservation remained idempotent with synthetic staged project data and after eviction; independently changed project ID, origin, object name, generation and move ID were rejected without changing that data. Before the fix, the missing-constraint fixture was accepted instead of rejected.

`node scripts/test-real-relocation.mjs` passed with a real Go-created project, one user, 17 audit rows and 59 tables. After the destination reached staged state, the test retried its reservation, evicted the owner, retried again, and compared owner state and per-table evidence before proceeding. The test also completed the existing relocation checks. Workerd logs contain expected errors from deliberately rejected calls and evictions.

A same-tuple reservation retry does not itself validate staged business-data ownership or the complete destination schema: later import and destination-manifest checks provide those separate checks. These local tests do not establish hosted writer drain, recovery/PITR semantics, detection of every possible database corruption, final artifact provenance, or authorization to move an actual singleton.
