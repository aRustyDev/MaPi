# Synthetic archive key-envelope provider

Status: **unmounted prototype; not a verified archive or independent recovery**. `worker/synthetic-archive-key-provider.js` is scoped to the existing synthetic KMS key and run. Its injected KMS client uses only the permitted `purpose` and `run_id` encryption-context pairs; it does not establish an AWS identity for a Woven Worker.

The provider conditionally reserves a distinct synthetic key slot before calling `GenerateDataKey`. Only a definitely acknowledged and read-back-verified new reservation may generate a key; `created:false` includes an uncertain acknowledgement and does not prove ownership. An uncertain or failed generation leaves the reservation claimed and cannot automatically generate again under that slot. The provider writes and reads back the wrapped-key envelope before returning a **provisional envelope digest**, never the plaintext key. It zeroes its mutable plaintext byte copies on completion or failure and best-effort zeroes late KMS responses after cancellation.

An open requires the caller to supply an independently trusted digest of the exact bounded envelope bytes; the provider compares that digest before parsing or KMS `Decrypt`, checks canonical envelope fields and exact synthetic KMS key/context, and verifies an HKDF-domain-separated HMAC binding the expected archive ID, manifest digest and wrapped key. It returns a non-extractable AES-GCM `CryptoKey` only after verification. A caller-supplied string is not itself proof that the commitment is independent: a party able to generate a new KMS data key can create another self-consistent envelope, so an independent authority must select and retain the exact digest. Archive payload nonce allocation, complete chunk history, ciphertext and seal formats, and authority for the expected manifest remain outside this prototype.

Focused evidence:

- `node scripts/test-synthetic-archive-key-provider.mjs` passed with injected KMS and object-store doubles. It covers simultaneous claims, lost reservation acknowledgment, uncertain generation, exact-digest and cross-archive rejection, late plaintext cleanup, non-extractable key use, and caller scope mutation during asynchronous calls.
- `node scripts/test-synthetic-archive-key-workerd.mjs` passed in disposable local workerd with a local R2 binding and an injected synthetic KMS double. It covers the local key-envelope round trip, concurrent reservations, and ambiguous reservation acknowledgment. Local loopback permission was used; no Woven deployment was accessed.
- `MAPI_SYNTHETIC_KMS_LIVE=1 node scripts/test-synthetic-archive-key-live.mjs` passed once against the existing synthetic AWS KMS key using the created writer and recovery roles. It generated and reopened one synthetic data key and exercised an AES-GCM round trip. The object store and expected digest were only in memory, and both roles were assumed via the same selected SSO profile. The roles' trust had previously been read back as the same IAM role; this live run checked account and assumed role names but did not pin source and role IDs. This is not independent custody or durable archive evidence.
- After that live run, `node scripts/test-synthetic-kms-cli-safety.mjs` passed offline. It covers a minimal child-environment allowlist and fixed `PATH`, configured-endpoint and CA override removal, exact role-ID checks, fail-closed system-CA and pinned-executable path validation, and zeroing late child-output buffers after timeout. The updated opt-in live script sets `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true`, forces the canonical macOS system CA bundle, pins the currently supported Homebrew AWS CLI entry point, and checks the previously verified source, writer and recovery role IDs. It has **not** been run against AWS with these changes. The current session was checked read-only and had no AWS endpoint/CA override environment variable names; the selected profile had no direct endpoint, services-endpoint or CA-bundle setting. This narrow observation does not prove all TLS, profile or host state for the earlier run.

The live test did not print or explicitly write temporary STS credentials or plaintext data-key material. Mutable byte buffers are cleared where controlled, but JavaScript strings and runtime/CLI-managed memory cannot be reliably zeroed; no forensic memory-erasure guarantee is claimed. The hardened script's CA check pins the canonical root-owned, non-writable macOS system bundle and fails closed on unsupported platforms, but does not prove the system trust store or host is uncompromised. The pinned Homebrew CLI entry point is a user-owned Python script; its path and mode checks do not verify the interpreter, imported modules, installation provenance or host integrity. The calling Node process also must be trusted: for example, `NODE_OPTIONS` may affect it before it builds the restricted child environment. Aborting stops the caller's wait, not a dispatched AWS request. A late plaintext KMS response is cleared best-effort. The synthetic bucket and commitment in the live test are not independent, and a permanently abandoned reservation is not resumable recovery. A real implementation must prove independently authenticated commitment and key custody, immutable durable storage and nonce allocation across retry/PITR, a complete authenticated archive, restore, retention and isolation before using this as a cutover gate.
