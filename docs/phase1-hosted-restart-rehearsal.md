# Hosted coordinator restart rehearsal

On 2026-11-19 the synthetic `application` singleton moved from generation 1 to generation 2 in a fresh Woven namespace set while the second synthetic project received concurrent Go-backed management reads. This is an interruption experiment, not a zero-error runtime benchmark or authorization to move the real singleton.

The synthetic owner used the frozen Phase 1 application, registry and Go Wasm with SHA-256 `979cdf5386076ef0bda76ef7e21e8a869a55726cbb8b3f9f5eb5d58e6e0fbc65`. A staging-only coordinator subclass added authenticated restart RPCs; these were reachable only through the fixed-project private control Worker, which had no public routes, custom domains, workers.dev or preview URLs. The public application ingress exposes no fault routes. Disabled deployed owner JavaScript and Wasm and control JavaScript were compared byte-for-byte with the local reviewed bundle before enabling the fixed synthetic move; the enabled code etags matched. The enabled owner uploaded at 54,971.14 KiB and validated startup in 119 ms. The fresh namespaces and approved 100% active versions were verified immediately before the run: owner `e0e533d3-be2a-4737-a856-3b429395a80c`, router `b3d8f5b3-28aa-43bc-ac00-26c77f037546`, private control `23537cb7-39b1-4335-86e8-079ab87bb812`. These are synthetic test versions; they predate later local recovery changes.

At each checkpoint the private coordinator wrote a durable stage marker, called `ctx.abort()`, and was probed through a newly resolved stub. The test required an intentional 503, a changed coordinator boot UUID and the prior boot UUID in the persisted marker before proceeding with the production coordinator's `advance` method:

- After source freeze at 23:25:24 UTC; the persisted source was `application` and the route stayed closed.
- After import chunk 2 at 23:25:26 UTC.
- After the registry CAS and before destination activation at 23:26:28 UTC.
- After destination activation and before source retirement at 23:26:29 UTC.

The run completed at 23:26:30 UTC after 119 production coordinator advances and 123 successful concurrent second-project `GetUser`/`QueryUsers` reads. Its registry journal contained 59 matching source/destination digest pages, including one original user and 31 historical audit events. The user page digest was `8ed19f24cd090a05d2656005703e3dabf62ca86d4192c9b9c7e8f31dd65eee59`; the historical event page digest was `bbdb37faaebe618e3118a6820a2cb2e9c219dd77b87bf5208ac5d4e459f66fd4`. The original project ID and user ID were preserved, the old source rejected a stale write, the existing active session worked and revoked session remained rejected. Existing credentials worked for each project, cross-project credentials were rejected, and a new destination user write/login succeeded while the other project rejected those credentials. A still-valid handoff was established separately in `phase1-hosted-handoff-repeat.md`; the handoff created for this longer restart run was not tested.

For 23:25:20–23:26:45 UTC, count-only Workers Logs returned owner 123 fetch `ok`, 4,561 RPC `ok`, four RPC `aborted` and two RPC `canceled`; router 123 fetch `ok`; control 192 fetch `ok`. Nonempty groups reported `sampleInterval: 1`. The four aborted coordinator invocations correspond to the intentionally injected restarts. The two canceled coordinator records were *not* deliberate aborts. Their RPC methods were `evidence`/`relocationEvidence`: the first at 23:26:29.455 (request prefix `62e733`, trace prefix `f52604`) followed an `ok` registry read and an `ok` control HTTP 200; the second at 23:26:29.516 (request prefix `e1a6b2`, trace prefix `2d2442`) also followed an `ok` registry read and an `ok` control HTTP 200. The driver consumed all 59 pages, but the reason Cloudflare classified those coordinator invocations as canceled is unresolved. Do not count this as a clean zero-error result without addressing or explicitly accepting those outcomes.

A subsequent read-only query of those two traces for 23:26:28–23:26:31 UTC reconfirmed the ordering with `sampleInterval: 1`. The retained driver output reports completion of 59 pages; the frozen driver parsed each evidence response and checked its cursor and sequence. The registry capped pages at 32 per response, but the driver output did not preserve request IDs, so associating the two trace records with those responses is an inference from method, timing and page limits. The timing is consistent with [caller-context cancellation](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/#request-cancellation), not proof of its cause; [HTTP 200 alone does not prove a complete body](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/http/#handle-canceled-requests). This narrow recheck does not establish full-window limit or periodic-memory coverage.

No `mapi.overload` log markers were found in the three Workers. CPU-bearing records covered 123 owner fetches and 897 owner RPCs, with p95/max 3/7 ms and 9/670 ms respectively; they do not cover all recorded RPCs. Router CPU data covered 9 of 123 fetches and control CPU data one of 192 fetches. Initial and delayed Durable Object periodic queries for all five involved objects returned no rows, so total isolate-memory coverage and periodic CPU/memory-limit counts remain unverified. A blank periodic result is not evidence of zero errors or a memory peak.

A later read-only GraphQL recheck of the synthetic owner namespace for 23:25:20–23:26:45 UTC returned six periodic groups across three objects. The largest returned `memoryUsageBytes` sample was 64,451,085 bytes; the latest group was timestamped 23:26:25 UTC, before the recorded 23:26:30 completion. The returned groups summed to zero `exceededCpuErrors`, `exceededMemoryErrors` and `fatalInternalErrors`. The query did not identify the roles of the three objects or establish coverage of every object and moment, and the final seconds remain unsampled. These values do not establish a true isolate peak, a complete zero-limit-error window, or evidence for the newer candidate. The four intended aborts and two unexplained canceled RPC outcomes described above remain unchanged.

The same delayed query also returned two periodic groups for one registry object and six for one coordinator object. Their largest returned isolate-memory samples were 17,301,220 and 27,000,548 bytes respectively. The returned registry and coordinator groups had zero CPU-limit and memory-limit counters; registry fatal-internal counters were zero, while coordinator fatal-internal counters summed to four. Each fatal-bearing coordinator group had count and average sample interval 1, with metric periods starting at 23:25:23, 23:25:24, 23:26:26 and 23:26:28 UTC. GraphQL describes `datetime` as the start of a metrics period, so the aggregate cannot establish that these four errors are the four deliberately injected aborts even though the counts and timing are consistent with that possibility. Latest registry and coordinator periods started at 23:26:23 and 23:26:29 respectively, before the recorded completion; true peak and complete limit-error coverage remain unverified. The user requested investigation of the coordinator fatal-error attribution; that investigation was interrupted before activation and remains incomplete.

Cloudflare documents that [`ctx.abort()` logs an uncaught JavaScript error](https://developers.cloudflare.com/durable-objects/api/state/#abort), but that documentation does not identify which periodic error counter, if any, records it. The four fatal-internal increments therefore cannot be attributed to the injected aborts on that basis alone. The reported memory values are [isolate-wide samples](https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/), not memory exclusively attributable to an individual object.

The local-only harness `node scripts/test-hosted-restarts-local.mjs` also passed all four stages. In local multi-Wrangler testing, the private control/caller had to be restarted to discard the aborted coordinator's stale RPC proxy; the hosted private control continued successfully without that workaround. The remote driver and setup are in `scripts/hosted-restart-*.mjs`; the coordinator/control extensions are `worker/phase1-restart-owner.js` and `worker/phase1-restart-control.js` and must only be used with newly generated synthetic namespaces and a no-route private control. Private fixtures, full journals, configs and provenance are retained at `/private/tmp/mapi-p1-hosted-restarts-20261119`, and the immutable source snapshot is `/private/tmp/mapi-p1-restart-code`.
