# Local SQLite invalid UTF-8 diagnostic

The SQLite bridge can silently change the value returned for a TEXT cell whose stored bytes are not valid UTF-8. In a disposable local comparison, the current generated baseline's `projects`, `users` and `user_attributes` table definitions accepted two distinct values in `user_attributes.value`: a quoted invalid byte with hex `228022`, and a quoted valid U+FFFD with hex `22EFBFBD22`. The column is `TEXT NOT NULL` and has no UTF-8 validity constraint. The probe populated synthetic parent rows with foreign-key enforcement enabled in the native database; the local SQLite Durable Object also accepted both rows.

Python's native SQLite 3.54.0, configured with `text_factory=bytes`, returned the original distinct byte sequences. On local Miniflare 5.20261118.0-beta/workerd, both direct `sql.exec` and the `worker/sql.js` query bridge returned the same JavaScript code points `[34, 65533, 34]` for both values. SQLite `typeof(value)` remained `text` and `hex(value)` remained distinct before and after those reads, so this observation demonstrates read-boundary conversion, not a write to the stored rows. A separate native query reported `json_valid(CAST(X'228022' AS TEXT)) = 1`; this does not establish application-level validity or workerd JSON behavior.

Run `node scripts/probe-invalid-sqlite-text.mjs` from the implementation checkout, after building the generated baseline and installing the locked dependencies. The diagnostic uses fresh in-memory native SQLite and a synthetic SQLite Durable Object with no existing object bindings or external target. It imports the current `worker/sql.js`; its fixtures and results contain no project data or credentials. The Miniflare listener is configured for `127.0.0.1`; that listener and local mode do not themselves enforce an outbound network restriction. The normal exit path disposes Miniflare; forced-interruption cleanup has not been independently verified. The baseline and dependencies used for this observation were from the working checkout, not a clean frozen build. The command exited zero on November 23, 2026.

This proves that the reconstructed schema and raw SQL permit the bytes, and that the local bridge cannot distinguish them on this read. It does **not** prove that a supported Go or HTTP handler can create this value or that any real project contains it. In particular, the pinned Go `insertUserAttributes` implementation marshals attribute values as JSON before insertion; JSON and Go's UTF-8 handling need separate end-to-end analysis. Native SQLite's byte-oriented Python read is not itself a native Go handler test. The evidence does not establish import behavior, hosted workerd behavior, exact platform limits or a general lossless recovery protocol. This diagnostic preceded the relocation policy below.

## Relocation policy for issue #10

Relocation rejects malformed stored TEXT. The owner scans the stored byte projections of the reviewed application tables before installing the source fence. The source inspection repeats after the fence is installed. Both fresh export and digest validate the stored bytes again before reading strings. Validation iterates rows and decodes each TEXT cell in 64 KiB slices, after materializing the complete cell as a BLOB. Each pre-freeze and frozen-source scan runs in one synchronous invocation without a total row or byte bound. A large scan can exceed hosted CPU or memory limits, and a failed frozen-source scan can leave the owner fenced. Hosted capacity and a resumable or bounded scan remain open before this policy is ready for a real move.

Transfer checkpoints without the current TEXT guard require manual review. Reconciliation requires version 3 evidence. A pending chunk or a previous journal is retained when rejected. Valid U+FFFD, ordinary multibyte text and a leading U+FEFF in a fragmented value round-trip. Import rejects an unpaired surrogate and rolls back the chunk.

`node scripts/test-usercreate-parity.mjs` sends malformed JSON attribute bytes, a valid replacement character and multibyte text through native NextGen and the pinned Go/Wasm user-create, admin-patch and self-patch HTTP routes. For these tested requests, both handlers accepted the malformed input and wrote the valid UTF-8 bytes for U+FFFD. The tests read the stored bytes from SQLite. This evidence covers the tested `user_attributes.value` path.

The isolated Woven staging harness uses a new registry and owner namespace. It provisions and writes through the same production-tagged Go/Wasm owner, checks that a synthetic malformed row is rejected before freeze without changing its bytes, and retries the same intent after removing that fixture row. It verifies export, import, transfer history, reconciliation and the existing cutover gate. The proof endpoint requires a separate staging credential and takes no caller-supplied fixture data. The synthetic staging result covers the fixture. Assessing an existing source requires a separate read-only check of its stored bytes.
