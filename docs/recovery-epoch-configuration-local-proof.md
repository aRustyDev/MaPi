# Recovery epoch configuration parsing

`MAPI_RECOVERY_OBJECT_EPOCHS` is an independently configured map from canonical Durable Object IDs to nonempty recovery eras. JavaScript's `JSON.parse` accepts duplicate JSON members and silently uses the last one; a duplicate entry can therefore select an era different from another entry for the same object. The configuration parser now rejects duplicate decoded keys, including names made equal by JSON escapes. It also requires the existing flat string-map format before interpreting entries.

`node scripts/test-recovery-epoch-configuration.mjs` passes locally. It checks valid flat maps, whitespace, string escapes, non-ASCII values, byte limits, missing and malformed values, duplicate members, escape-equivalent keys, and duplicates for non-target objects. The existing validation of canonical lowercase object IDs, nonempty/nonzero eras, and the 128-byte encoded era limit remains in force. Valid unique flat maps keep the same decoded values; duplicate or non-string members fail closed, even when a later duplicate would have overwritten them.

This is a parser unit test, not a deployment or end-to-end recovery proof. It does not establish recovery provisioning, external epoch deployment, invalidation, point-in-time restore, or safe reopening; recovery remains disabled.

The parser rejects era strings containing unpaired UTF-16 surrogates; valid surrogate pairs and the existing 128-byte UTF-8 limit are preserved. `node scripts/test-recovery-epoch-configuration.mjs` passes in Node, where different lone surrogates encode to the same SQLite value. `node scripts/test-recovery-epoch-text-runtime.mjs` passes in disposable local workerd: SQLite stored the two malformed values as distinct bytes (`EDA080` and `EDBFBF`), but reading them back produced indistinguishable JavaScript strings. Valid supplementary-plane eras remained distinct. These tests demonstrate local serialization behavior only, not end-to-end recovery or hosted behavior.
