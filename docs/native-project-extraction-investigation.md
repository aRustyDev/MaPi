# Project extraction preflight investigation

The full native database snapshot in [native-sqlite-import-proof.md](native-sqlite-import-proof.md) fails the per-project tenant boundary. A correct filtered export needs more than `WHERE project_id = ?`: the generated pinned baseline has 55 non-SQLite tables, including the global authorization catalog and its relation/closure tables, the migration ledger, and project rows keyed by `id`. Event sinks may be global. More importantly, an authorization assignment is stored in the **protected** project and may refer to a user or team in another project without a composite foreign key. Conversely, grants held by a project's users or teams can live in other project databases. Filtering only by the target project silently breaks those relationships.

`scripts/project-extraction-preflight.mjs` is a **read-only investigation helper**, not an importer or an authorization decision. It compares source table names and column metadata to the generated pinned baseline, counts target assignments whose user/team principal does not exist locally, counts assignments elsewhere that refer to target users/teams, and identifies ambiguous duplicate IDs, unresolved membership users and lifecycle-owner teams, principal types it does not understand, non-system catalogs and shared event sinks. It outputs aggregate counts and schema names, not principal identifiers or record contents. It intentionally reports `safeToExport: false` for every input.

After generating the pinned baseline with `node scripts/baseline.mjs`, inspect a **quiesced local copy** of a native SQLite database and run the synthetic regression test:

```sh
node scripts/project-extraction-preflight.mjs /path/to/local-nextgen.sqlite PROJECT_ID
node scripts/test-project-extraction-preflight.mjs
node scripts/test-native-project-preflight.mjs
```

The regression test uses the real baseline in temporary SQLite databases. It checks inbound and outbound foreign user/team grants, unresolved and ambiguous principal IDs, missing membership and lifecycle-owner references, unsupported principal types, shared sinks, non-system catalogs, added tables and changed columns. It also checks the command-line path opens its source read-only. The second test creates two synthetic native projects and users, stops the native server, inserts synthetic cross-project grant rows directly into that local test database, and verifies that the preflight detects inbound and outbound user grants. Those SQL inserts are test setup, not grant-API coverage. These checks do not establish an exhaustive dependency analysis or verify a real exported destination.

Even a zero count cannot authorize extraction. This helper does **not** inspect every semantic reference, audit payload, JSON document, blob, project secret, foreign identity, credential, delegation, release, event-sink cursor or custom catalog dependency. A source table with a project column can still contain foreign information in a row or payload. It does not compare table constraints, indexes, triggers or schema migration semantics; column matching alone is insufficient. Unsupported principals in other projects may refer to the target by mechanisms this helper cannot resolve, and system catalog data is not compared. Active writes can invalidate results unless separately fenced. The schema check and counts must not be used as a security boundary or as proof of tenant isolation.

Before implementing filtered import, inventory ownership and reference closure for **every table and field**, including opaque content and global records, and define how cross-project principals, ownership, grants, events and keys migrate. Demonstrate the full source and destination inventory, foreign-row and foreign-content absence, transactional consistency, a quiesced source, authenticated transport and conflict/recovery handling with representative native deployments. Until then, there is no safe filtered exporter in this repository.
