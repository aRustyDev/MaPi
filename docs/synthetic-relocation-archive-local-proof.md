# Synthetic encrypted archive: local prototype

Later work added a separate bounded sealing path and version-2 synthetic verification heads; see `synthetic-archive-bounded-sealing-local-proof.md`. The earlier evidence below describes the implementation as tested at the time and does not validate those newer changes.

`worker/synthetic-relocation-archive.js` is unmounted and synthetic-only. It uses the existing synthetic KMS key-envelope provider and the bounded create-only object helper; it does not change a source, move a route, delete replay chunks, or establish an independent archive authority. The caller must provide an independently authenticated frozen-source commitment and a separately trusted key-envelope digest. This code cannot establish the authority of those inputs.

Each source chunk is kept byte-for-byte after reassembly and is checked against its source SHA-256 chain, project, generation, move, table order, expected count and terminal digest. Each chunk is split into exactly two independently authenticated AES-GCM parts. An encrypted descriptor binds both part digests, source length and source digest. The seal binds the ordered descriptor and part selector/ciphertext inventory and the full source commitment. Reservations bind each index to its content before encryption. Each encryption attempt first burns a distinct random 96-bit nonce through a create-only reservation; uncertain claims are never used, and ambiguous or failed attempts are not reused. A conditional immutable selector chooses the verified attempt. Orphan reservations and unselected attempts are retained. Reservation metadata includes project, origin, source object, move identifiers and hashes in application-readable plaintext; bucket access controls must protect it.

This nonce protocol requires an independently held unique data key per archive and a store that prevents deletion, overwriting or rollback of nonce reservations and selected objects for the entire key lifetime. A store that merely implements conditional writes does not prove this requirement. The reader checks for missing, unexpected or conflicting committed selector keys; these paginated listings are not atomic and require separately enforced writer closure. The legacy one-scan implementation limits a single selector listing to 4,096 pages and performs initial verification in one invocation. The separate bounded verifier can advance one page or up to eight chunks at a time, conditional on an independently trusted authority as described below. The per-record object cap is 128 KiB. A synthetic 131,072-byte source chunk produced a largest encrypted object of 109,357 bytes; this does not measure hosted limits or the SQLite row boundary.

The restore driver first authenticates the complete archive and seal before beginning an inaccessible staged destination. The target interface must independently enforce fresh target state, atomic/idempotent import and a durable checkpoint bound to the authenticated identity, seal and inventory. On retry, the driver reads the seal and resumes chunk data at the stored cursor rather than re-reading or reinserting earlier committed rows; legacy mode still lists selector metadata at completion; verified-head mode relies on the earlier completed listing and externally enforced write closure. The driver cannot prove the target's access controls, checkpoint authority or row integrity by inspecting the interface alone, and it does not activate a project.

Run `node scripts/test-synthetic-relocation-archive.mjs`. It uses a filesystem-backed R2-like test store, a synthetic KMS test double, and a local SQLite staging database with transactional row/checkpoint writes. It covers conflicting content, concurrent retries, an ambiguous nonce claim, a lost selector acknowledgement, failed attempt upload, bad key/project/commitment, swapped/missing/extra selector or part, corrupt ciphertext, missing seal, full verification before first staging write, interruption after row writes, rollback, restart and checkpoint resume without reinserting committed rows. It reads existing local source strings only; it is not a real-owner import, hosted R2, real-key archive, independent key-custody or PITR/retention proof. It uses a tiny synthetic dataset, not the representative Phase 1 dataset.

Before any move can depend on this component, integrate and verify the actual production destination and its route fence, source commitment authority, protected nonrollback storage, independent recoverable key custody, authenticated complete inventory and staged-data reconciliation, access and retention policy, write closure, resumable large-archive verification, and real-key/independent-store restore with representative data. The separate interrupted registry/history and real-owner proofs remain open. Never delete source replay chunks or relax the retired fence on the basis of this local test.

It archived two synthetic chunks, restarted the local R2 runtime, verified the seal and chain, and restored two users and one audit row into a separate local SQLite checkpoint fixture. It made one GenerateDataKey and five Decrypt calls, stored 32 R2 objects totaling 13,525 bytes, had a largest object of 797 bytes, and took approximately 6.0 seconds. The fixture supplied its own expected commitment, both roles were assumed from one SSO identity, and the target was a local SQLite test adapter. The run used no Woven deployment and did not explicitly persist credentials or plaintext data keys. This run preceded the later selector-ordering and resumable-verifier changes and was not repeated after them. It does not prove independent authority, separate identity custody, hosted R2 retention/write closure, a representative-size import, or real-owner recovery.

The later, separate `beginSyntheticVerification` and `advanceSyntheticVerification` prototype verifies at most eight chunk records or one selector-list page per call. It stores encrypted immutable checkpoints tied to the exact archive identity, source commitment, key-envelope digest, seal and inventory. Each checkpoint head includes a monotonically increasing revision and the digest of its predecessor; a caller must supply a separately pinned current head, and the independently authenticated authority must enforce the exact predecessor and revision with linearizable, nonrollback create/CAS operations. Heads use their exact canonical JSON property order: reordered encodings fail closed. The authority, verifier identity and pinned-head custody are required external trust dependencies, not established by this module. A stale or untrusted head is rejected when it differs from the current trusted authority; if both the authority and independent pin can be rolled back or forged together, this component cannot detect it. Archive write closure, selector-list stability and retention must hold throughout verification and restore.

The focused Node test now also covers one-chunk verification batches without rereading earlier chunk objects, an exact lost-CAS acknowledgement resolved by rereading the authority, failure before CAS, a failed reread after CAS that remains uncertain, stale and rolled-back pinned heads, a foreign identity, a corrupted encrypted checkpoint, same-page and cross-page duplicate selectors, missing/extra selectors, and a repeated listing cursor. The authority in that test is an in-memory single-writer stand-in; the test does not prove durable, independent, authenticated or nonrollback authority. If both a CAS acknowledgement and the authority reread are uncertain, the call fails and an independently authorized operator must reconcile the head; it does not infer success or retry a KMS operation.

A later `MAPI_SYNTHETIC_KMS_LIVE=1 node scripts/test-synthetic-archive-kms-r2-live.mjs` run exercised the **current bounded sealing, verification and restore paths** using the existing synthetic KMS key and roles, disposable local Miniflare R2, and a local SQLite authority double. It closed and reopened both local R2 and the authority database after sealing, verified two chunks, restored them in two bounded calls, and compared both user records, the audit record, per-chunk digests and the final chain and inventory. The successful run made one data-key generation and 15 decrypt calls, stored 73 local objects totaling 38,204 bytes, and took 9.5 seconds. Credentials and plaintext keys were not printed or explicitly saved. Both roles still trust the same administrator; the fixture supplies its own commitment, and its local authority and destination do not establish independent custody, protected hosted retention, or a real-owner restore. The legacy-path run above is separate historical evidence.

The synthetic restore driver can optionally consume a completed verifier head and skip the legacy initial scan. It authenticates the current head and complete encrypted checkpoint before touching a destination, binds the head digest to the durable target checkpoint, and rechecks authority before and after target mutations and before returning. Verified restore processes at most eight chunks per invocation; a partial result carries the next index. This relies on the independently authenticated authority making completed heads terminal and immutable and on an archive namespace that is write-closed, nondeletable and nonrollback throughout verification and restore. The rechecks cannot revoke an in-flight target transaction: a mismatch after dispatch leaves the target staged for reconciliation. The legacy mode still uses its own full scan. Synthetic tests exercise the new integration, but an independent authority, a representative Nextgen dataset and production restore have not been established. The separate legacy seal operation still scans the complete archive in one call; bounded sealing is exercised by the later KMS run above.

The local workerd composition `node scripts/test-synthetic-archive-combined.mjs` passed with a synthetic authority, local R2 and the actual chunk importer. It tested a changed head on a fresh target, a head change after an importer commit, bounded progress and an interrupted commit/acknowledgement retry without re-reading or reinserting an earlier chunk while a second synthetic project ran concurrently. The authority reset used by the fixture is test-only and is not an operational reconciliation procedure. This is not hosted, independent-authority, representative-size or real-owner evidence.

The read RPC itself is not revoked, mutations remain awaited, and cancellation does not automatically impose a deadline or establish production reconciliation, independent custody, representative scale or hosted behavior. ## Restore checkpoint reference isolation

A distinct same-isolate synthetic destination reproduced a mutable-reference defect in `restoreSyntheticArchive`: its `apply` callback changed the supplied next-checkpoint object to a terminal value. Before the fix, the driver used the same modified object as its readback expectation and reported completion after only one of two chunks. The destination was a deliberately malicious local test double; this is not evidence of a deployed owner failure.

The driver now copies bounded, primitive checkpoint fields on reads and passes detached checkpoint objects to destination callbacks. The native `node --unhandled-rejections=strict scripts/test-synthetic-relocation-archive.mjs` test now rejects the modified readback, keeps the synthetic destination incomplete, and rejects oversized, extra or nonprimitive checkpoint fields before invoking destination writes. The existing synthetic bounded-sealing and verifier-runner Node tests also pass. This hardens the unmounted protocol against shared-reference mistakes; a destination that lies consistently or loses data can still report an expected checkpoint. The real staged target must enforce atomicity and independently reconciled data, and source commitment, independent custody, nonrollback storage, retention, full-history verification and the registry cutover gate remain open. The interrupted combined Workerd and scale fixtures were not run.
