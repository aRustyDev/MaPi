# Audit source-row capture: local implementation boundary

`worker/audit-source-capture.js` is a private, unmounted helper; no production Worker, RPC route, schema migration, or Woven deployment calls it. It is a step toward staging a selected audit event, not an audit snapshot or an authorized audit API.

For one trusted selector's canonical signed SQLite `rowid`, it checks the owner fence and recovery era and invokes a trusted synchronous read-only authority callback inside one `transactionSync`. It checks the source project in SQL as TEXT under binary collation. A fixed list of the 25 event columns follows the pinned `eventQuery`. SQLite copies scalar INTEGER, REAL and NULL values directly to staging; it copies TEXT and BLOB values as at most 64 KiB BLOB fragments, recording the source storage class. Source bytes do not cross into JavaScript during copying. SQLite inserts the fragments and the scoped row marker atomically. Source and capture schema checks reject unexpected column names, extra capture indexes and triggers, and source triggers. The callback and selector are trusted inputs; the helper does not obtain or authenticate them.

An existing marker for the same scope and source row is replayed only when the currently present source agrees with all retained fragments, storage types, scalar values and part counts. A missing or changed source fails closed. REAL replay is deliberately rejected because SQL numeric equality does not establish bit-exact identity. A deletion followed by byte-identical reinsertion with the same rowid and project cannot be distinguished: a trusted immutable source version is still needed. No independent commitment authenticates the staging rows; a writer able to alter source and staging together can forge agreement.

## Focused native test

`node scripts/test-audit-source-capture.mjs` passed on Node 26.9.0 in a disposable in-memory SQLite database using the events DDL from the generated pinned baseline. It covered a negative and a zero rowid; a different project's row; TEXT and BLOB values spanning multiple fragments; an INTEGER above JavaScript's safe range without reading it through JS during capture; changed and deleted source rows and changed rowid reuse on retry; injected mid-copy rollback; denial at the final authority check; a rejected staging trigger; stale recovery era and owner fence; and alternative NOCASE source-project and recovery-era columns. The case-insensitive schemas must not make a different project or epoch match. It did not exercise the exact platform size boundary, nonfinite values, malformed SQLite TEXT, the interrupted cursor work, or hosted resources.

The first focused attempts failed at empty default TEXT fields: native SQLite returned NULL for `substr` of an empty BLOB. The helper now stores an explicit zero-length BLOB fragment for empty TEXT/BLOB. The final command above exited 0 after that correction and the two binary-collation checks.

## Temporary-schema guard

The separate native command `node scripts/test-audit-capture-temp-guard.mjs` first failed because a TEMP trigger attached to the main fragment table was not visible in `sqlite_schema`, so capture completed rather than rejecting it. The unmounted helper now checks `sqlite_temp_schema` and rejects temporary objects shadowing the source or capture table names, and temporary triggers attached to those tables. This check fails closed if the runtime cannot query the temporary schema. The command then passed: a temporary trigger and uppercase temporary staging and source tables were rejected with no marker or trigger side effect, and capture succeeded after their removal. `node scripts/test-audit-source-capture.mjs` also passed after the guard change.

These are native SQLite results only. The temporary-schema query has not been checked in workerd, and the helper remains unmounted. The guard does not establish protection for the authority or fence tables, independent schema authority, or a complete snapshot. It does not exercise the pending handler diagnostic or interrupted fragment-transfer test.

## Unresolved integration requirements

- The source check validates the fixed column names and excludes triggers, but does not prove complete source DDL, affinity, primary-key shape, or all schema semantics. It cannot be assumed compatible with other supported schema versions. The owner fence helper itself materializes route control fields, so total JavaScript memory is not bounded by this component.
- The supplied authority callback must be synchronous, read-only, and must not schedule mutation; its Boolean result is not proof of actual Go handler authentication, project visibility, or registry authority. The current owner route and recovery-state transitions must be wired and validated before use.
- One atomic row copy does not select the right rows, preserve a consistent view across multiple events, protect against retention, or prove correct scan errors, filters, pagination, tie ordering or public serialization. A durable event-version or write/retention-fence design and full handler parity remain necessary. The source version must also bind the selection to the copy.
- The staging tables contain sensitive plaintext. Their access controls, lifecycle, deletion, quota reservations, storage exhaustion, crash recovery, authenticated whole-history verification and general idempotent retries are not implemented. An interrupted copy rolls back locally, but an acknowledged copy cannot be replayed after the source disappears.
- The fragment bound controls individual transferred SQLite values, not SQLite-internal memory, aggregate storage, CPU or transaction time. The helper has not run in workerd or been measured against Worker size, startup, isolate-memory or hosted load gates. The 25-column query and repeated fragment reads need validation on the configured Cloudflare runtime.
