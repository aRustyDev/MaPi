# Local login enumeration experiment

**Private experiment; do not mount or deploy.** The pinned default login flow reveals whether an email exists: a known identifier advances to the password step, while an unknown identifier advances to registration. This difference is observable both in the browser and in the flow API response.

The test-only adapter publishes a login-only flow requesting email and password together. For unknown identities it invokes `domain.UserPassword.Verify` against a synthetic, randomly generated hash from the same upstream hasher, then returns the same generic failure response as a wrong password. On either failure it denies access to the failed flow and issues a fresh upstream flow. No synthetic user is created, and success still goes through the real upstream challenge and handoff exchange. The adapter includes test-only per-IP and object-wide limits; it is not wired into the application.

**Critical gap: failure counter continuity.** Nextgen records a failed password proof on its challenge for rate-limiting and audit. Replacing the failed flow creates a different challenge, so the original challenge's failure count is not carried forward. In this pin the flow adapter also issues a new challenge for each submit, and the SQLite challenge upsert resets the count. A source search found no production reads of `GetFailureCount` or `GetLastFailedAt`; this does not prove that all indirect enforcement paths or consumers are absent. The isolated admission budget below is deliberately stricter than this observed behavior, not native counter parity. It does not replace the original per-challenge records or prove equivalent auditing. This experiment must not be deployed until upstream state and effective abuse protections are resolved and tested against native behavior, including retries, concurrent requests, eviction and restore. Creating new flows also accumulates provisional session and flow records; retention and resource bounds are not implemented.

## Private per-identifier admission experiment

The test-only owner now keeps a **rolling 12-admission / 15-minute** budget for an identifier, in addition to its existing per-IP and object-wide limits. It derives a project-scoped HMAC of the NFKC-normalized, lowercase identifier using a separate synthetic secret; the ledger stores only HMAC digests and timestamps. It charges the existing IP/object budgets synchronously before HMAC and upstream work, including for malformed submissions and invalid flow cookies. It rechecks the flow after the asynchronous HMAC operation, verifies the upstream flow cookie, then checks and charges the identifier in a second synchronous SQLite transaction before submitting the proof. These are separate transactions. All eligible submissions, including successful or operationally failed requests, consume an admission, so this is an availability-conservative experiment, not a failure-only counter. It does not copy or modify the upstream challenge's counter or replace its audit record.

When an identifier budget is exhausted, the experiment runs the same dummy password verifier for either known or unknown identifiers and returns the same generated failure response and cookie attributes, rather than exposing an identifier-specific 429. IP and object-wide limits still use 429 and apply independently of account existence. The owner blocks even a correct password while the budget is exhausted, then permits requests when the rolling window expires. The test seeds equal ledger histories for a known and an unknown identifier, races two fresh-flow requests with different IPs at the boundary, checks their common response and canonicalized key, verifies persistence after object eviction, and simulates budget expiry by aging stored timestamps. It also forces an actual upstream authentication attempt to expire and verifies that even the correct password cannot obtain a handoff. A forged flow cookie cannot charge the identifier budget or invalidate another browser's flow; concurrent invalid-cookie requests remain subject to the IP gate. No user or authenticated factor is created by these failure paths. The observed equality of individual responses is not a proof of timing or traffic-history indistinguishability; in particular, a known account's prior legitimate activity can affect the admission decision. Local cookie lengths varied by one byte even for independently generated cookies from the same fresh-flow generator, so the test checks attributes, not exact length equality or indistinguishable length distributions.

The HMAC normalization is a conservative prototype and has not been proved to match every identifier schema, alias and Unicode equivalence used by Nextgen. The budget can be used for targeted denial of service; key rotation, bounded cleanup and table quotas, durable audit for blocked requests, policy changes, all other ingress paths, clock behavior, recovery/relocation eras, broader flow-expiry races, legacy hash costs, and distributed abuse controls remain open. The test's seed and aging methods are privileged diagnostic controls, not production APIs. An audit or limiter error must fail closed without exposing different behavior. There is no deployed handler or hosted proof, and these checks do not resolve the original deployment blocker.

## Reproduce

From the MaPi root, with the pinned upstream checkout and dependencies already prepared:

```sh
node scripts/test-enumeration-browser.mjs
```

The test starts local HTTPS workerd and Chromium using a generated certificate pinned by its SPKI. It builds `wasip1` with the test-only `mapi_enumeration_test` tag and does not deploy or call external services. It checks equivalent error JSON after removing generated IDs, status and cookie attributes, no password echo, no credential-authenticated session factors or new user, rejection of flow cookies by `/sessions/me`, rejection of discarded flow IDs, shared per-IP and per-identifier admission under concurrency, eviction and simulated expiry, cross-project rejection, a valid password followed by real handoff exchange and authoritative session read, and the official component's identical error for both failures.

One local run measured five alternating warm failures per case: unknown median **270.9 ms**, wrong-password median **268.9 ms**; the Wasm artifact was **55,590,342 bytes**. This small local sample is not evidence of constant-time behavior or hosted capacity. The experiment uses the pinned default hasher; accounts with legacy or different hash costs, cost upgrades, lockouts and other factor types require their own side-channel analysis. A robust production design also needs bounded cleanup, authoritative multi-project and origin isolation, uniform error and throttling behavior for all failure states, failure injection, load testing and hosted memory measurements. There is no guarantee that normalizing a response alone hides an account's existence.
