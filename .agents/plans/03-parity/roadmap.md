# MaPi roadmap from the Woven prototype to full ZITADEL Nextgen parity

## Destination

**MVP:** On Woven staging, an operator provisions a project, deploys a login configuration, and registers an OIDC client. The official `<zitadel-login>` component signs a user into an independent relying party. Two projects run side by side with separate data, keys, issuers, and sessions. The entire MVP runs on Workers and Cloudflare bindings.

**Full parity:** MaPi reproduces the shipped behavior of pinned, self-hosted Nextgen **v0.7.0** across the server, Console, CLI, SDKs, and operational workflows. The MVP issuer is an additional deliverable. The pinned native server mounts issuer scaffolding, denies issuer admission, and leaves the provider endpoints unimplemented. Use the existing upstream Go OAuth package and complete that path as a testable extension. [Pinned release](https://github.com/zitadel/nextgen/releases/tag/v0.7.0) · [Pinned issuer implementation](https://github.com/zitadel/nextgen/blob/b0b74cd4a198428ea9b82910c217259ffc62b65c/apps/api/internal/oauth/server.go) · [Nextgen protocol design](https://github.com/zitadel/nextgen/blob/b0b74cd4a198428ea9b82910c217259ffc62b65c/docs/adrs/082-oauth-and-oidc-server.md)

## Phase 4 · Verify and release full parity

- **Close the native comparison.** Pass every shipped operation and additional route in the inventory, the upstream Console, CLI, and SDK suites, and the MVP issuer conformance suite. Compare permissions, status codes, response bodies, cookie behavior, transactions, and audit effects. Normalize generated IDs and timestamps in the harness. Require a passing test for each shipped behavior before calling it parity.
- **Rehearse operations at multiple-project scale.** Run sustained and burst traffic with a hot project beside normal projects. Demonstrate canary deploys, forward schema migration, compatible rollback, emergency key rotation, encrypted backups, project relocation, and restore. For relocation, quiesce writes, copy and reconcile records, switch the registry route, and reject writes from stale routes. After restore, invalidate affected sessions and pending handoffs before reopening traffic. Rehearse import from a native Nextgen deployment with representative IDs, grants, password hashes, passkeys, and audit history. Preserve issuer and RP ID where credential portability depends on them.
- **Apply the Cloudflare fallback rule.** For a full-parity feature that still misses a measured Workers limit after reducing its dependency graph and bounding its work, move only that workload to a Cloudflare Container behind a private Worker binding. Keep authoritative writes and audit commits with their Durable Object owner. Require the same parity, isolation, failure, recovery, and load tests before accepting the fallback. [Cloudflare Containers](https://developers.cloudflare.com/containers/)
- **Publish the operator handoff.** Deliver the parity inventory, workload envelope, deployment and recovery runbooks, and an inventory of any container workloads. Review the pinned server and Console licensing and corresponding-source distribution before wider rollout. [Nextgen licensing](https://github.com/zitadel/nextgen/blob/b0b74cd4a198428ea9b82910c217259ffc62b65c/LICENSING.md)

**Optional follow-on:** A production ZITADEL v4 replacement gets its own compatibility and cutover plan. It covers REST, gRPC and gRPC-Web, SAML on both sides, SCIM, Actions and webhooks, legacy token and grant behavior, the instance and organization model, and migration from the PostgreSQL event store and projections. Its acceptance gate is a representative cutover with existing clients and credentials.
