# Phase 1 progress: runtime and storage boundaries

**Status: blocked and incomplete; not ready for a real singleton cutover.** This is a snapshot of the implementation and evidence available on 2026-11-23. The [Phase 1 roadmap](roadmap.md) remains the source of the intended scope and exit gate. This commit captures work in progress, including unmounted experiments and unresolved tests; it is not an approval to deploy or migrate.

The Phase 1 implementation started from MaPi `12555ef02d60d5ee76f328319dc988db75fc6833`, with Nextgen v0.7.0 at `b0b74cd4a198428ea9b82910c217259ffc62b65c`. The separate Phase 0 report at MaPi `d30e245` records a clean-build baseline, hosted fixture, compatible rollback and synthetic single-object point-in-time restore; it does not establish recovery safety for the newer fenced multi-project candidate. The original Woven singleton has not been moved.

## Hosted runtime

- The existing isolated owner uses an origin registry, a SQLite Durable Object per project and Workers Static Assets. Two newly provisioned projects passed hosted browser isolation. Historical owner version `7caf7302-b9cd-4c91-a5fa-f3c05672bf52` uploaded at 54,404.93 KiB and validated startup in 106 ms; its mixed burst measured warm sign-in p95 of 4.58 s and 5.34 s. An earlier window recorded 16 memory-limit errors. See [hosted staging evidence](../../../docs/hosted-staging.md).
- A later synthetic fence-aware candidate, owner version `2a0cbb6b-701d-4cc4-91de-46850493110b`, uploaded at 54,966.26 KiB and validated startup in 107 ms. Both projects completed 20 journeys per project in each phase. Sign-in p95 was 4.652 / 5.254 s without management and 9.632 / 5.218 s with management, in owner-origin / router-origin order. The user accepted those measured latency values and sampled-memory limitations **for that candidate**; [issue #1](https://github.com/aRustyDev/MaPi/issues/1) tracks the performance debt. The original 3.5 s target and the other gates have not been waived for later candidates. See [hosted runtime evidence](../../../docs/phase1-hosted-runtime.md).
- The earlier harness did not retain intermediate browser HTTP failures or validate management-read identities, so completed journeys alone do not prove the absence of unexpected errors or correct readback. The revised harness checks those outcomes, signed RP claims and replay responses, paired sign-in and full-journey samples, and client-side overlap; focused local tests passed. It has not run end to end against the final candidate. The benchmark's provenance guard remains closed, and `phase1Pass` remains false until the required evidence is established. See [runtime harness evidence](../../../docs/phase1-runtime.md) and [benchmark inventory limitations](../../../docs/phase1-benchmark-inventory.md).
- The final fence-aware artifact still requires exact build and deployment provenance, uncompressed size at most 55 MiB per Worker, startup validation at most 750 ms, a cold measurement, both 20-journey-per-project bursts at concurrency four, and complete CPU, memory, overload and error evidence. Keep Argon2 settings unchanged and report Wasm pages separately from total sampled isolate memory. A local dry run below the size limit is not hosted startup or load evidence.
- A later dirty local flow/issuer/management owner dry run measured 55,170.68 KiB uncompressed. In local Workerd, an earlier bundle completed 20 login-and-session journeys per project with management reads and two operator creates per project; each create was read back and matched an audit event. Request-boundary Wasm high-water samples reached 106,168,320 bytes (1,620 pages) per owner. These artifacts predate further source changes, use legacy login rather than the browser-to-RP timing endpoint, and do not prove total isolate memory, hosted limits or acceptance. See [local build](../../../docs/phase1-owner-current-size-diagnostic.md) and [local mixed load](../../../docs/local-owner-management-write-load-diagnostic.md).

Miniflare source indicates its persistence path may have been configured incorrectly, but the cause was not established and the test was not rerun pending the user's decision. The new reactor attempt markers have separate local Workerd evidence using real Go and synthetic stubs; that does not resolve the restart or hosted cold-start gate. See [restart diagnostic](../../../docs/local-owner-cold-restart-diagnostic.md) and [reactor markers](../../../docs/reactor-attempt-markers-local-proof.md).

It also lists Workers Editor; the policy inspections were read-only. ## SQLite bridge and representative import

- Native pinned SQLite statements, dialect and migration packages passed. Workerd passed 283 of 285 original statement functions; the remaining two native held-lock schedules cannot be reproduced faithfully by the synchronous WASI runner. An independent concurrent-owner equivalent passed, but its rerun with the later stricter result classifier was interrupted before dispatch. Five passing functions used simulated timer waits. The bridge and all 39 migration checks passed locally. Snapshot comparisons cover columns, foreign keys, indexes and tokenized `CHECK` expressions; the captured pinned native and workerd migration snapshots had no application views or triggers. These comparisons do not prove all SQL semantics or trigger behavior. See [bridge matrix](../../../docs/sqlite-bridge-matrix.md) and [schema migration proof](../../../docs/schema-migration-proof.md).
- A local actual-Go-owner transfer passed with 10,000 users, 100,037 historical audit events, 172,572,894 encoded bytes, 2,102 chunks and 67 reconciled tables in 126.38 seconds. It exercised a real credential, active/revoked sessions, original issuer-key signature, stale-source rejection, interrupted transfer, replay and zero foreign-key violations while a second project used sessions. The 9,999 bulk users shared a synthetic hash and salt, one bulk credential was checked, dependencies were symlinked, and the run predates later source changes. It is local evidence, not final-candidate hosted sign-off. See [relocation evidence](../../../docs/relocation-proof.md) and [selected source hashes](../../../docs/phase-1-large-import-valid-credential-sha256.json).
- **Open integrity defects:** `npm run test:sql-returning-exact` fails with `SQLITE_TOOBIG` for a platform-valid row because bridge metadata enlarges a `RETURNING` result. Production query results also lack bounded materialization. A synthetic transfer converted SQLite REAL infinity to NULL while source and destination digests matched. The current guard rejects non-finite values and a journal guard blocks some old unfinished moves; this is containment, not lossless transfer. Existing active destinations and old writers need separate reconciliation. The importer also rejects some rows below the platform maximum. Do not use the current protocol for a real move. See [checkpoint guard limitations](../../../docs/relocation-checkpoint-guard-local.md).
- The importer now snapshots chunk content and digest before asynchronous hashing, rejects case-varied control-table names and duplicate SQLite identifiers, and detects case-varied main-schema control triggers. Focused native and local Workerd tests passed. Small Workerd transfers also checked credential BLOB and NULL values, rollback, replay and project isolation; they are not representative-scale or real-owner evidence. A separate importer-control investigation was stopped by a safety flag and remains unverified. See [envelope integrity](../../../docs/relocation-envelope-alias-local-proof.md), [control-table checks](../../../docs/relocation-control-table-names-local-proof.md), and [credential transfer](../../../docs/relocation-credential-workerd-local-proof.md).
- Pre-freeze validation now checks bounded returned catalog metadata, schema and clock state, recovery epoch, origin and project identity, and repeats authoritative checks after freeze. It does not yet preflight all row values, foreign ownership or dependencies, bound every underlying scan, or establish freshness while writes continue. Unsupported data can still be found after maintenance starts. Full representative interruption, retry and reconciliation evidence must be rerun on the final candidate after these defects are fixed.

## Singleton fencing and rehearsal

- The local implementation integrates registry generations, owner admission and relocation checkpoints. Local real-owner and four-restart rehearsals have exercised stale-write rejection, same-move retries, identity preservation, active/revoked sessions and concurrent second-project management traffic. The updated local rehearsal validated 119 management responses and six client-side login/session overlap samples; these do not prove hosted server-side overlap or full legacy-writer coverage. See [owner fencing](../../../docs/phase1-owner-fence.md) and [local rehearsal](../../../docs/phase1-synthetic-rehearsal.md).
- A synthetic Woven restart rehearsal completed four injected coordinator interruption points, reconciled 59 digest pages and made 123 concurrent second-project reads. Four aborts were intentional, but two evidence RPCs were classified as canceled. A later periodic aggregate reported four coordinator fatal-internal errors; the count and timing are consistent with the intentional aborts but do not prove attribution. The user requested further investigation, which was interrupted before activation. Sampled memory and limit metrics also did not cover the entire run. The restart rehearsal did not demonstrate overlapping login and session traffic on both origins; its handoff expired. A separate shorter move demonstrated one successful still-valid handoff exchange and rejected replay. These separate results do not complete the combined hosted rehearsal. See [restart rehearsal](../../../docs/phase1-hosted-restart-rehearsal.md) and [handoff repeat](../../../docs/phase1-hosted-handoff-repeat.md).
- Before cutover, prove every writer has adopted fence-aware code and drain old in-flight work. A 100% Worker deployment alone is insufficient: a Durable Object can continue serving on old code during deferred update. The pre-freeze intent and post-freeze source fence must be reconciled with legacy writers, all mutation paths, recovery and stale direct RPCs. A failed pre-freeze check can retain an intent; old unfinished journal states and already-frozen exhausted-generation moves need explicit recovery. See [owner fencing and deployment caveats](../../../docs/phase1-owner-fence.md).
- **New cutovers are blocked pending an independent encrypted-archive authority.** Direct `ProjectRegistry.commitRelocation` now rejects new cutovers while allowing retries of already-committed moves. The synthetic KMS writer and recovery roles share an administrator, so independent custody remains open. A trustworthy move-bound source commitment, independent nonrollback retention, staged-owner reconciliation and a verified restore are still required before implementing a positive authorization path. Starting a move can still freeze the source. See [archive cutover gate](../../../docs/relocation-archive-cutover-gate.md) and [custody requirements](../../../docs/archive-key-custody-requirements.md).
- A new local Workerd test verifies an archive with the synthetic authority Durable Object, survives authority eviction and restores into the actual chunk importer. A separate local archive-only 128 MiB fixture verifies exact restored bytes and interruption checkpoints. Both use synthetic data and fake KMS; neither establishes an independent authority, hosted retention or a representative real-owner restore. See [staged archive proof](../../../docs/synthetic-archive-staged-local-proof.md) and [archive scale proof](../../../docs/synthetic-archive-scale-local-proof.md).
- Owner retirement now checks the retired fence tuple and logical update count in its transaction, and rejects tested main-schema fence triggers. Native and local Workerd helper tests passed; the application method also passed with native SQLite and a synthetic registry. This does not establish a real-owner or hosted cutover. See [retirement evidence](../../../docs/owner-retirement-postcondition-review.md).
- The bounded audit snapshot remains unmounted. Local experiments add fenced reader leases, bounded ordering fragments, a transactional spool/checkpoint seam and a Go-to-host snapshot-start transaction. The last uses synthetic authorization, not the pinned handler's actual access and visibility checks. The reported sort differential has incomplete branch coverage, and its test-source inspection was aborted; the audit checkpoint eviction test was also aborted. The user chose to leave both evidence items open. Handler parity, authenticated checkpoint authority, bounded total work and hosted behavior remain unproved. See [audit requirements](../../../docs/audit-bounded-snapshot-requirements.md), [Go transaction diagnostic](../../../docs/audit-shadow-go-transaction-workerd-local-proof.md), and [sort checkpoint evidence](../../../docs/audit-shadow-sort-checkpoint-local-proof.md).
- Coordinated restore and reopening remain disabled. Per-scope recovery high-water, hosted PITR behavior, old-writer drain, session and handoff invalidation, and a fresh recovery era remain unproved. The separate local recovery-batch proof failed with `Invalid provisioning route`; it is not passing evidence. The platform may hold time fixed during synchronous work, and the local frozen-clock counterexample leaves strict authentication expiry at commit unresolved. See [split-password and clock limits](../../../docs/upstream-split-password-proof.md).
